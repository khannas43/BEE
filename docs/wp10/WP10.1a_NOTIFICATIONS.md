# WP10.1a — In-portal notifications (the backend half)

**Status:** Implemented locally on branch `wp10-notifications`; the full local gate passes (see Evidence). **Not independently reviewed or accepted.**

**Provisional local rules, not BEE rules.** The owner's decision D10 ([BEE_DECISIONS.md](../BEE_DECISIONS.md), [WP10_PLAN.md](WP10_PLAN.md)): in the portal only, to everyone in the application's organisation, for four events: returned, rejected, fee due, approved.

## What it does

- **Written by the events themselves.** A trigger on each record those events already write (return, rejection, fee snapshot at submission, certificate) inserts one `notification` row for every active member of the application's organisation (active membership, active organisation, active account), in the same transaction. A step cannot succeed without its notification, and no Java code can forget one. The text holds only what the applicant may already read (a reason, the fee, the registration ID and validity) and never names a person.
- **Append-only.** A notification never changes except that its recipient marks it read, once; the runtime login can only read the table and mark through two functions (`notification_mark_read`, `notification_mark_all_read`).
- **Spring:** `GET /api/notifications` (the caller's own, newest 50, with the unread count), `POST /api/notifications/{id}/read`, `POST /api/notifications/read-all`. Someone else's id, an unknown id and a malformed id all get the same `404 not_found`. Any signed-in caller with an effective role may use them; each reads only their own.
- **Portal:** the same three routes under `/api/runtime/notifications`, each validated like every other upstream answer. Contract 0.24.0; the request logs know all six routes.
- **No Idempotency-Key on the two mark-read writes**, an explicit exception recorded in the contract (`x-bee-idempotency.x-exceptions`): marking read never goes back, so repeating it changes nothing.
- **Cleanup:** the disposable-application cleanup (V39 re-creates it) deletes notifications first.
- **No backfill:** applications decided before this migration have no notification (BL-149).

## Tests and evidence

- **Gate:** `npm run local:check`: **1410 passed, 0 failed**, including `repo.lint-clean` (0 problems), contract coverage (2175/2175 live observations conform; 396/396 internal and 546/546 browser pairs evidenced) and the Secretary live check (127 checks over two runs). Migration count 39 in every database test.
- **Spring contract** (`SpringContractTest.notificationOperationsDocumentedPairs`): no token, identity denials, own list, empty list, mark one (twice), unknown and malformed id, mark all, database down.
- **Web:** `notifications.test.mjs` (validators), three `session_expired` unit-evidence tests; `web:test` 198, `web:test:ui` 77.
- **Live** (Secretary check): the applicant sees the fee-due and approval notifications with the registration ID; the text contains no account name, username or address (60 names checked); an officer's own list holds nothing for the application and marking the applicant's notification gets 404 and leaves it unread; the applicant marks one read (once), an unknown id is 404, read-all leaves none unread; one approval notification per organisation member.
