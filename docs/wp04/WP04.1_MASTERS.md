# WP04.1 — Effective-dated masters (local foundation)

Status: **correction implemented locally, awaiting review.** The review of 1 October 2026 (`15e1246`) found a blocker: under V4's immutable-row and overlap guards, a seeded open-ended version could never be superseded. V5 adds a controlled, attributable closure-and-successor operation (§3). WP04 is not accepted and the work-package count stays **1/11**. Branch `wp04.1-masters`, from `0c97af6`.

This activity persists five internal masters: appliance categories, applicable standards, laboratory accreditation, fee rules and rating-formula metadata. Every row records its source, verification status, version and effective period. Spring can resolve the version that applies on a given date. No browser screen, API route, permission, administration write, model submission, fee confirmation or rating computation uses these masters yet. WP04.2 owns the organisation, agency and brand workflows. WP05.1 (submission: category, standard, accreditation and fee) and WP05.2 (rating) will consume these rules when they build those actions.

**Nothing here is BEE-approved.** Every seeded row is `synthetic` or `provisional`, and none is `verified`. The fee amounts and the placeholder rating formula must not be shown as official, and no star rating is computed.

## 1. Schema (`V4__effective_dated_masters.sql`, `V5__master_supersession.sql`)

Each master has its own table in schema `app`. All five share these columns:

| Column | Meaning |
| --- | --- |
| `id` | uuid, generated |
| `rule_key` | The key that versions are compared within (below) |
| `version` | Positive integer; `UNIQUE (rule_key, version)` |
| `effective_from` | First calendar date the version applies (inclusive) |
| `effective_to` | First calendar date it no longer applies (exclusive); `NULL` means open-ended; must be later than `effective_from` |
| `source_reference` | Where the value came from; must not be empty |
| `verification_status` | `synthetic`, `provisional` or `verified` |
| `note`, `legacy_id`, `recorded_at` | Free note; the V2 row it replaced, if any; insertion time |

| Table | `rule_key` | Payload |
| --- | --- | --- |
| `master_category` | category code (`^[A-Z]{2,10}$`) | `name` |
| `master_standard` | `category:purpose` | `category_code`, `purpose`, `standard_code`, `title`, `edition` |
| `master_lab_accreditation` | `laboratory:category` | `laboratory_code` (references `organisation.code`), `category_code`, `accreditation_body`, `certificate_ref`, `accreditation_status` (`active`, `suspended`, `withdrawn`) |
| `master_fee_rule` | `category:application_type` | `category_code`, `application_type`, `amount_inr numeric(12,2)` |
| `master_rating_formula` | `category:star_rating` | `category_code`, `formula_label`, `inputs` (JSON array), `definition` (JSON), `computation_allowed` (may be true only when `verified`) |

Database guards apply to every master table:

- **No overlap.** A `BEFORE INSERT` trigger takes a transaction advisory lock on the table and rule key. It then refuses a new version whose `[from, to)` range overlaps any other version of the same key, with SQLSTATE `23P01`. Since V5, the comparison uses each version's *effective end*: its closure date if it has been closed (§3), otherwise its `effective_to`. Periods that only touch are allowed. An open-ended, unclosed version blocks any later start. If the incoming (rule key, version) already exists, the trigger leaves it to the unique constraint. That way a repeat seed's `ON CONFLICT DO NOTHING` still skips a version that has since been closed. A trigger is used rather than an exclusion constraint so that no `btree_gist` extension is needed.
- **Immutable history.** `UPDATE`, `DELETE` and `TRUNCATE` are refused with `55000`: "versions are immutable … add a new version for a later period". This applies to the version rows and, since V5, to closures. An open-ended version is ended only by the closure operation in §3, never by editing the row.
- **Upgrade path.** V4 copies the V2 `fee_rule` and `rating_formula` rows into the new tables as version 1, keeping their ids in `legacy_id`. It then drops the two V2 tables. V5 adds only the closure table and functions, and it replaces the body of the overlap function. It changes no rows. Nothing in the existing data is lost.

`master_closure` (V5) holds one row per closed version:

| Column | Meaning |
| --- | --- |
| `master_table`, `rule_key`, `version` | The closed version; primary key, so a version can be closed only once |
| `effective_to` | The closure date: the first date the closed version no longer applies, and the successor's `effective_from` |
| `successor_version` | The version inserted with the closure; unique per key; must be greater than `version` |
| `closed_by`, `source_reference`, `reason` | Who closed it, on what authority and why; none may be blank |
| `recorded_at` | When the closure was recorded |

## 2. Date boundary convention

A version applies on date `d` when `effective_from <= d` and either its effective end is null or `d < end`. The effective end is the closure date for a closed version and `effective_to` otherwise. This is a half-open range `[from, to)`: the start date is included and the end date is excluded. When one version ends on 2026-10-01 and the next starts on 2026-10-01, the old version applies through 30 September and the new one from 1 October. Dates are calendar dates in India Standard Time. The caller converts any instant to an IST date before asking. WP05.1 and WP05.2 must still decide which business date they supply, for example the submission date or the fee-confirmation date (decision M7).

If no version covers a date, the lookup returns **no rule**. This happens before the first version and in a gap between versions. The service never falls back to the nearest version. If two versions ever matched one date, the repository would throw instead of choosing one; the overlap trigger prevents that state.

## 3. Closing an open-ended version (V5)

The only way to close a version is the database function `master_supersede(table, rule_key, version, closure_date, closed_by, source_reference, reason, successor)`. The successor is a JSON object of the new version's payload and provenance, keyed by column name. The function works the same way for all five master types. In one statement it:

1. checks that the table is one of the five masters, a closure date is given and the successor is a JSON object. It refuses a successor that sets `id`, `rule_key`, `version`, `effective_from`, `legacy_id`, `recorded_at` or an unknown column (`22023`);
2. takes the same advisory lock as the overlap trigger for that rule key;
3. writes the `master_closure` row. Its trigger refuses:
   - a closure not made through the function (`42501`);
   - an unknown version (`P0002`);
   - a second closure (`23505`, "already closed");
   - a version that already has an end date, since only an open-ended version can be closed (`22023`);
   - a closure date on or before the version's start (`22023`);
   - a blank actor, source or reason (`23514`);
4. inserts the successor as version max + 1, starting on the closure date, open-ended unless it supplies `effective_to`. The normal table checks and the overlap trigger apply, so an invalid amount, a successor ending on its own start, a missing column or a computable unverified formula is refused;
5. returns the successor's version.

A failure at any step aborts the statement, so the closure and the successor are written together or not at all. A deferred constraint trigger also requires, at commit, that every closure has its successor starting on the closure date.

The closed row keeps its payload, provenance and recorded `effective_to = NULL`. The closure records when the handover happens and who made it, on what authority and why. Both are immutable. Nothing is closed in the seed or the shared runtime; `local:check` asserts 0 closures there.

The function has no permission check of its own. It is reachable only through `MasterDataRepository.supersede`, and no controller, route or permission calls that. Who may call it, and whether a closure date may lie in the past, are BEE decision M6.

## 4. Spring API (internal)

The code is in package `gov.bee.api.masters`. It has no controller and is not referenced by any route or permission.

- `MasterDataRepository` provides `category`, `standard(category, purpose, at)`, `labAccreditation(lab, category, at)`, `feeRule(category, type, at)`, `ratingFormula(category, at)` and `history(table, ruleKey)`, using JdbcTemplate. Lookups join `master_closure` and resolve on the effective end. The one write is `supersede(table, ruleKey, version, closeOn, closedBy, sourceReference, reason, successorJson)`, which calls `master_supersede`.
- `MasterVersion` carries the recorded `effectiveTo` and an optional `Closure` (closure date, successor version, actor, source, reason, recorded time). `effectiveUntil()` is the effective end.
- `MasterDataService` provides:
  - `categoryApplies`;
  - `applicableStandard`, `feeRule` and `ratingFormula`, which return empty unless the category itself applies on that date;
  - `accreditation`, which returns `ACCREDITED`, `SUSPENDED`, `WITHDRAWN` or `NO_RECORD`. A suspended or withdrawn record that is in force is **not** an accreditation.
- Each record has `beeVerified()`. `RatingFormula` deliberately has no compute method.

## 6. The ₹1,000 / ₹24,000 fee discrepancy

The two sources disagreed:

- FIRST_SLICE.md provisional decision **D6** says "one seeded rule: ₹24,000 for room air conditioners", citing DDD §5.3 (gap G08).
- The V2 local seed (`fee_rule` RAC-DEMO) held **₹1,000.00**. It has no source, and was a local placeholder.

Neither value was silently chosen, and neither is BEE-approved. Both are kept as separate, labelled versions of `RAC:new_model`:

| Version | Amount | Period | Status | Why |
| --- | --- | --- | --- | --- |
| v1 | ₹1,000.00 | `[2026-01-01, 2026-10-01)` | `synthetic`, `legacy_id = RAC-DEMO` | The existing V2 row, preserved unchanged by the V4 migration; source recorded as "local placeholder; no source" |
| v2 | ₹24,000.00 | from 2026-10-01, open-ended | `provisional` | The D6 figure; source "FIRST_SLICE.md provisional decision D6, citing DDD §5.3 (gap G08); not confirmed by BEE" |

So a lookup for 30 September 2026 returns ₹1,000 and a lookup for 1 October 2026 returns ₹24,000, each with its provenance. The split date is synthetic. It does not mean BEE changed the fee on that date. The tests assert the amounts, statuses, sources and boundary. `local:check` (`db.provisional-rules`) asserts the same state in the running database. BEE must still decide the real amount, the application types, tax treatment and effective date (M4). A future BEE-confirmed rule will be a new `verified` version, added by closing v2 with `master_supersede` on BEE's effective date. The throwaway-schema tests do exactly this with a test-only verified ₹30,000 successor. Neither seeded row is edited.

## 7. Rating formula

The formula master holds metadata only. The seeded `0-unverified` version has an empty definition and `computation_allowed = false`. A database `CHECK` refuses `computation_allowed = true` unless the row is `verified`, and the Spring model exposes no way to compute a rating. The prototype's `computeStars` thresholds are not copied into the master. Any rating shown by the prototype still carries `0-unverified` and is not an official star rating (FIRST_SLICE.md D3). WP05.2 owns computation once BEE supplies a verified formula (M5). That formula would be added by closing v1 with `master_supersede`.

## 9. Limits

- There are no administration writes, routes or permissions. Rows enter through migration and seed SQL, plus the internal `master_supersede` operation, which only the tests call.
- `closed_by` is free text from the caller. It is not tied to a signed-in user or a role, because no route calls the operation yet. When an administration action is built (WP04.2), it must pass the authenticated actor and check permission first.
- Only an open-ended version can be closed. Shortening a bounded version, correcting a wrong payload or withdrawing a version outright is not supported (M6).
- A closure date may lie in the past relative to the recording date. That would change what resolves for dates already passed. Whether that is allowed is part of M6; the closure records `recorded_at` so it can be detected.
- Accreditation is keyed to the seeded `LAB` organisation. WP04.2 owns organisation workflows.
- Standards are keyed by category and purpose only, without model sub-types or star bands.
- `RT1` (`rt1-proof.sh`) has been updated to count the new tables but was not run, because it is destructive.
- There is no audit event for master changes; WP04.3 owns master-data audit tests.
