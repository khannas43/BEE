# WP04.2b-2 — Registration review and approval (R1)

**Status:** Implemented locally on branch `wp04-registration-2` (14 October 2026). **Not accepted.** WP04 stays open at 1/11. Evidence and review are recorded below as they are completed.

**Provisional local rules, not BEE rules.** The owner accepted these defaults on 14 October 2026 ([WP04.2b_PLAN.md](WP04.2b_PLAN.md)): Programme reviews and recommends; the Director approves; the approver is never the person who filed or recommended the request.

## What exists

| Part | Behaviour |
| --- | --- |
| One command | `POST /api/registrations/{id}/transition` with `{action, version, note?}` and an `Idempotency-Key`. Answer: a receipt (`registrationId, reference, action, fromState, toState, version, actedAt`, plus `registeredBrandId` or `registeredAuthorisationId` on approval). |
| Programme | `recommend` (programme_review to director_approval); `return` (to returned, a reason is required). |
| Director | `approve` (to approved); `reject` (to rejected, a reason is required); `return` (to returned, a reason is required). |
| Applicant | `resubmit` a returned request (to programme_review). No second fee: the fee snapshot and confirmation stand. A returned request can be edited (PATCH) and its licence replaced (a new version) before resubmitting; the same gates as a submit apply. |
| Second person | Nobody who filed a request reviews it; nobody reviews a request of their own organisation; the approver is never a person who recommended it. Checked in the service and again in the database (trigger on the transition event, and inside the approval function). |
| Register entry | Approval runs in the database function `registration_approve`: it checks the capability `registration_approve` (Director), the version, the second-person rule, then writes the `brand` row (owner is the applicant organisation, status active, provisional, the reference as source) or the `agency_authorisation` row (agency, principal, brand, period, active, provisional). A clash (a name already registered, an overlapping authorisation) comes back as a refusal and nothing is written. |
| Legal moves | A trigger allows only draft→fee_due→programme_review→{director_approval, returned}, director_approval→{approved, returned, rejected}, returned→programme_review. |
| Reading | Programme reads the review and approval stages and the decisions after; the Director reads the approval stage and the decisions; the applicant reads its own requests. `GET /{id}` adds the `trail` (the applicant sees only the decisions and their reasons; reviewers see every step) and, once approved, `registeredBrandId` or `registeredAuthorisationId`. |
| Privileges | `ensure-runtime-role.sh` now takes INSERT, UPDATE and DELETE on `brand` and `agency_authorisation` from the runtime login: the only way it can write the register is the approval function. |
