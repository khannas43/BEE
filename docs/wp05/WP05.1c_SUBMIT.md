**Status:** review corrections implemented locally; not accepted. WP05.1 and WP05 remain open; overall count 1/11.

## Scope

- `GET` / `POST /api/model-applications/{id}/submit` (Spring) and `/api/runtime/model-applications/{id}/submit` (BFF).
- Filing manufacturer or authorised agency on **own** draft only; brand/agency recheck from Spring DB at submit time.
- Category, performance-test standard and `new_model` fee rule must exist for submission date; missing rule → `422 rule_not_available` (fail closed).
- Fee snapshot at submit: amount, currency, rule key/version, verification, provenance; ₹24,000 RAC seed labelled **local demo** (`localDemoFee`, `label`), not BEE-approved.
- Atomic `draft` → `fee_due`, version increment, one submission event + one fee row per application; idempotent POST replay with filing-org recheck.
- POST binds `version` and `expectedFee` (amount, rule key/version); drift → `409 fee_preview_conflict` with no transition.
- UI: save-before-submit when the edit form is dirty; confirm shows persisted `draftSummary` and provisional fee; stored fee on GET list/detail after reload.
- V10+ append-only on submission event and fee tables (no `bee.test_cleanup` bypass); disposable cleanup via `app.app_disposable_model_cleanup()` as `bee_local_maint` only, with `local_disposable_application` registry (V11–V20).

## Independent review of `0bc2cea` (2 October 2026)

**Status:** two focused blockers remain; WP05.1c is not accepted. The stated test suite can pass while these boundaries are unproven.

1. **The API login still owns the protected tables.** The live database reports owner `bee_app` for `app.model_application_submission_event`, `app.model_application_fee_snapshot`, `app.model_application` and `app.local_disposable_application`. Spring's `application.yml` uses `bee_app` as its runtime datasource and Flyway login. The new test proves direct DELETE and cleanup-function calls are refused; it does not prove the runtime login cannot use owner DDL to disable or replace the append-only trigger. Give Spring a separate restricted runtime login with only necessary DML and function privileges; keep Flyway ownership/migration credentials separate. Prove, using the actual runtime login, that ALTER/DROP/DISABLE TRIGGER and direct UPDATE/DELETE/TRUNCATE of the protected records fail, while submit and registered maintenance cleanup still work. Do not edit already-applied migration files.
2. **Browser contract coverage is overstated.** `contract-coverage.cjs` maps every `/api/runtime/model-applications/{id}/submit` status/code pair to `SpringContractTest.submitOperationsDocumentedPairs`. The generated matrix accordingly counts browser-only or BFF-specific responses with no browser-boundary observation (for example, 401 `unauthenticated`, 403 `mfa_required`, 409 `idempotency_in_progress`, 422 `validation_failed` and 503 `service_unavailable`). A Spring MockMvc response cannot establish the Next.js route's status, body validation, headers or error translation. Count Spring evidence only for Spring operations; add focused live, stand-in or route-unit evidence for each browser submit pair, or report it honestly as uncovered. Audit the pre-existing draft-route mirror by the same rule. Keep the overall 220-pair figure qualified until the browser rows are evidenced.

**Independent verification:** `npm run api:test` passed; `npm run local:check` finished **268/268**, with seeded OTP credentials and sessions unchanged and no test identities left. A rollback-only PostgreSQL transaction with `SET LOCAL ROLE bee_app` successfully ran `ALTER TABLE app.model_application_submission_event DISABLE TRIGGER reject_row_change`; `tgenabled` was `D` inside the transaction and `O` after rollback. No protected record or trigger state was persistently changed.

The V11–V20 maintenance function, direct-DML refusal, dirty-form check, Flyway test expectation and observed submit paths are useful progress. They do not close the two boundaries above.
