# WP08.1a — Fee-rule administration (Wave 2 start)

**Status:** Implemented locally on branch `wp08-fee-rules-admin`; the full local gate result is in Evidence. **Not independently reviewed or accepted.**

**Provisional local rules, not BEE rules.** These are the owner's assumptions A1 and C1 of 4 October 2026 ([BEE_DECISIONS.md](../BEE_DECISIONS.md)); no fee here is confirmed by BEE.

## What it does

`/app/administration/fee-rules` (menu entry for the Administrator) lists every fee rule with its versions, dates, amount and tax line, and lets authorised people change them:

| Rule | Behaviour |
| --- | --- |
| Who | A person whose role holds the `fee_rule_manage` **permission**. The Administrator holds it now; giving it to another role is a database row (`capability_grant`), no code change. Everyone else gets 403 `role_not_permitted`. |
| Propose | Category, application type, fee, tax rate (a separate line), a start date that is **today or later**, a source and a reason. Nothing changes yet. |
| Approve or reject | A **different** permission holder. The proposer is refused (`segregation_refused`) however many roles they hold. |
| Withdraw | Only the proposer, while it is pending. |
| Take effect | On approval the version in force ends on the new date and the new one starts there, in one step (the existing close-and-start). A date that has passed while the proposal waited is refused (`effective_date_passed`); a date that clashes with the rules in place is refused (`rule_conflict`) and the proposal stays pending. |
| Nothing already issued changes | An application keeps the fee captured when it was submitted. |
| Tax | Stored on the rule as a rate in percent and shown as its own column (0 means not set). **Not yet added to the fee an applicant pays** (BL-132). |
| Application types | A table (`fee_application_type`); only `new_model` is filed today. |

The refusals are enforced in one database function, `fee_rule_decide`, which is the only way the runtime database login can change a fee rule at all (it cannot update a proposal or write a rule version directly). A refusal is returned as a result, so nothing is half done.

## What changed

- **Flyway V33:** `capability_grant`, `fee_application_type`, `fee_rule_proposal`, `master_fee_rule.tax_rate_percent` and `fee_rule_decide()`; grants for the runtime and maintenance logins (`ensure-runtime-role.sh`, `ensure-maint-role.sh`).
- **Spring:** `gov.bee.api.feerules` (repository, service, controller); three new error codes (`proposal_not_pending`, `effective_date_passed`, `rule_conflict`).
- **Contract 0.17.0:** `GET /api/fee-rules`, `POST /api/fee-rules/proposals`, `POST /api/fee-rules/proposals/{id}/decision`, on both layers; BFF routes, contract module, request-log registrations.
- **Web:** `components/app/admin/FeeRules.tsx`, `lib/client/runtimeFeeRules.ts`, a menu entry for the Administrator.
- **Tests:** `FeeRuleDatabaseTest` (8), a documented-pairs test in `SpringContractTest`, `fee-rules.test.mjs`, five screen tests, stand-in and unit evidence for the browser pairs, and the live check `npm run local:fee-rules` (72 checks over two runs).
- **Docs:** BL-131 updated, BL-132 narrowed, BL-136 and BL-137 added.
