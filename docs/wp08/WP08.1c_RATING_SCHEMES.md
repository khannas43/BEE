# WP08.1c — Rating schemes as configurable data (BL-134)

**Status:** Implemented locally on branch `bl134-rating-formula`; the full local gate passes (see Evidence). **Not independently reviewed or accepted.**

**Provisional local rules, not BEE rules.** The owner has no formula (decision A2, 4 October 2026) and asked for it to be configurable. What is configurable here is the **efficiency-figure bands**; every scheme entered is still a LOCAL DEMONSTRATION, not a BEE-approved formula, and every rating computed from it still says so (`basis = local_demo`).

## What it does

`/app/administration/rating-formula` (menu entry for the Administrator) lists every scheme (the lowest efficiency figure that earns each of 1 to 5 stars, its category, its start date, whether it is in force) and lets authorised people add one, the same way as a fee rule (WP08.1a):

| Rule | Behaviour |
| --- | --- |
| Who | A person whose role holds the `rating_scheme_manage` **permission** (the Administrator now; another role later by a database row). Everyone else gets 403 `role_not_permitted`. |
| Propose | Category, a start date that is **today or later**, five figures each higher than the one before (1 to 99.99, two decimals), a source and a reason. |
| Approve or reject | A **different** permission holder; the proposer is refused (`segregation_refused`). Only the proposer may withdraw. |
| Take effect | Approval adds the scheme (five bands under a new key such as `RAC-ISEER-2`). The rating step already uses the scheme with the latest start on or before the day it computes, so nothing in the rating code changed. Two schemes of one category may not start on the same day (`rule_conflict`); a start date that passed while waiting is refused (`effective_date_passed`). |
| Nothing already issued changes | Earlier schemes stay; every rating keeps the scheme key it was computed with. |

The refusals live in one database function, `rating_scheme_decide`. The runtime login can no longer write the master tables, the closures or the rating bands directly (it holds only the right to run the two decision functions): this also closes a gap in WP08.1a (BL-140).

## What changed

- **Flyway V35:** `rating_scheme_proposal`, `rating_scheme_decide()`, the `rating_scheme_manage` permission, and the runtime login's write privileges on the master tables removed (also in `ensure-runtime-role.sh`, which would otherwise grant them back).
- **Spring:** `gov.bee.api.ratingschemes`; no new error code (it reuses `proposal_not_pending`, `effective_date_passed`, `rule_conflict`).
- **Contract 0.19.0:** `GET /api/rating-schemes`, `POST /api/rating-schemes/proposals`, `POST /api/rating-schemes/proposals/{id}/decision`, both layers.
- **Web:** `components/app/admin/RatingFormulas.tsx`, `lib/client/runtimeRatingSchemes.ts`, the menu entry.
- **Tests:** `RatingSchemeDatabaseTest` (8), a documented-pairs test in `SpringContractTest`, `rating-schemes.test.mjs`, five screen tests, stand-in and unit evidence, and the live check `npm run local:rating-schemes` (72 checks over two runs, using schemes that start in the year 2100 so they never apply to a real rating).
- **Docs:** decision A2, BL-134 done (demonstration), BL-139 and BL-140 added, a correction to the WP08.1a note.
