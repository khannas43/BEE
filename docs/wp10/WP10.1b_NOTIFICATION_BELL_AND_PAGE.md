# WP10.1b — The notification bell and the Notifications page

**Status:** Implemented locally by Cursor (Brief 10) on branch `cursor/notifications-ui`, reviewed and gated by Claude; the full local gate passes (see Evidence). **Not independently reviewed or accepted.**

**Provisional local rules, not BEE rules.** The owner's decision D10 ([BEE_DECISIONS.md](../BEE_DECISIONS.md), [WP10_PLAN.md](WP10_PLAN.md)): in the portal only, whole organisation, four events. This package is the part the applicant sees; the server half is [WP10.1a](WP10.1a_NOTIFICATIONS.md).

## What it does

- **The bell** in the top bar replaces the prototype's fixed "7": it appears only for a signed-in Spring identity (never for the development role preview, never on public pages), shows the unread count (hidden at 0, "9+" above 9), says "Notifications, 3 unread" to a screen reader, and links to the page. It reads on load, on focus, when the tab becomes visible and every 30 seconds while visible. A failed read shows no badge and no error.
- **The page** `/app/model-label/notifications` (menu entry "Notifications", Hindi सूचनाएँ, for manufacturers and agencies) lists the latest 50, newest first, with a kind label, the application reference, the time, an unread dot, **Open** (returned: edit and send again; approved: the printable certificate; fee due and rejected: the application) which also marks the entry read, **Mark read**, and **Mark all read**. The bell and the page update together without a reload. The server's text is shown as plain text.
- **`runtimeAction`** (`lib/client/runtimeHttp.ts`): a POST with no body and no Idempotency-Key, for the two mark-read writes (the recorded contract exception).
- Four stray macOS duplicate files that were tracked in the repository are removed (three byte-identical ones by Cursor; `ProposalPanels 2.tsx`, an unused older draft, by Claude).

## Review findings

- **Fixed by Claude:** the client's id check required RFC 4122 version and variant digits, while the server accepts any 8-4-4-4-12 hex id. A notification on a seeded fixture application (ids like `…-4000-c000-…`) made the whole list an invalid response, so the page showed neither items nor the empty state and the bell no badge. Cursor's tests used random ids and could not see it; found by a browser probe. The pattern now matches the server's, with a regression test.
- Noted, not changed: the bell and the page each run their own 30-second refresh, so the identity is re-read twice per tick; marking one read triggers two list reads. Officers also see the bell (an empty list, BL-148).
