# WP09.1c — The public verification page

**Status:** Implemented locally on branch `wp09-public-verification`; the full local gate and a re-run of the Secretary check pass (see Evidence). **Not independently reviewed or accepted.**

**Provisional local rules, not BEE rules.** The owner's default D8 ([WP09_PLAN.md](WP09_PLAN.md)): anyone may check a registration ID without signing in and sees only the registration ID, manufacturer's legal name, brand, model, category, stars, efficiency figure, validity dates and the status. No personal names, addresses, application references, notes or internal ids. Every answer says it is a local demonstration, not a BEE certificate.

## What it does

`/verify?reg=<registration ID>` (the address the QR code carries) and `/verify` with a typed ID. The page asks the portal's `GET /api/runtime/verification?reg=…`, which asks Spring's `GET /api/public/verification?reg=…`. Results: **valid**, **expired**, **not yet valid** (computed from the dates in Indian time when read), **not found**, or "not available right now". The old prototype scenarios and ledger are gone.

## The first public route, and how it is kept narrow

- **Spring** allows exactly one new unauthenticated route, `GET /api/public/verification`; everything else stays default-deny (the contract tests prove a POST is still refused).
- **By construction:** the route reads only the database view `public_certificate` (V38), and the runtime login has `SELECT` on that view only for this purpose. A database test lists the view's columns, so a private field cannot be added without failing it.
- **No enumeration:** a malformed ID and an unknown ID return the same `404 not_found`; the pattern check runs before any database query; the ID is a bound parameter. A blank ID is `422 validation_failed`.
- **The portal route** sends no cookie or token upstream and reads no session; the browser fetch omits credentials. Answers are validated like every other upstream answer (exact keys, stars 1–5, dates, status, always `localDemoCertificate: true`), and `Cache-Control: no-store` applies.
- Contract 0.23.0; request logs know both routes (no query string is logged).

- Web: `public-verification.test.mjs` (validator), `verifyPage.test.tsx` (no call until an ID is given, valid, expired, not found, unavailable, credentials omitted).
- Live: the Secretary check, with a browser that never signs in, follows the QR address: both layers answer 200 without a token with exactly the public fields; unknown, malformed and blank IDs get 404/404/422 at both layers; the page shows the registration ID and manufacturer and the demonstration notice, shows no application reference or account name, and says "not found" for an unknown ID.
