# WP07.1h — Permanent rejection (Wave 1)

**Status:** Implemented locally on branch `wp07.1h-reject`; local checks pass (see Evidence). **Not independently reviewed or accepted.** WP05.2 and the first slice remain open; the work-package count stays 1/11.

**Provisional local rules, not BEE rules.** This completes [FIRST_SLICE.md](../wp01/FIRST_SLICE.md) section 4: "Any scrutiny, rating or approval stage ──reject (reason required)──▶ rejected (terminal). A new application is needed to try again."

## What it does

`POST /api/model-applications/{id}/reject` (browser route `/api/runtime/model-applications/{id}/reject`), with a version and a reason.

| Rule | Behaviour |
| --- | --- |
| Who | The owner of the stage the application is in: the assigned IAME officer (`iame_scrutiny`), the assigned Reviewer (`bee_scrutiny`), **Programme (`rating`)**, the Director (`director_review`), the Secretary (`secretary_approval`). Programme can only reject, never return, so this is its only way to say no. Finance (the fee) does not reject. Anyone else, including the applicant, gets 403 `role_not_permitted`. |
| Separation | The applicant's own organisation, or anyone who acted at a different stage, gets 403 `segregation_refused`. An officer who is not assigned gets the same 404 as an unknown application. |
| Reason | 1 to 500 characters, no control characters. The applicant sees it. |
| Atomic write | One transaction: the state becomes `rejected`, an append-only transition event, an append-only rejection record (one per application) with the stage it came from, the reason and who rejected it, and **every open assignment of the application is closed**. |
| Terminal | Nothing applies to a rejected application any more: it cannot be returned, rejected again, moved forward, edited or resubmitted, and no officer can read it. A returned application is with the applicant, so no officer can reject it either. |
| The model number | It is free again. The one-live-application-per-model rule already ignored rejected applications (V24), and a live check proves the same applicant can file a new application with the same model number and have it accepted. |
| Idempotency | A key is required. A repeat with the same body returns the stored receipt (header `Idempotency-Replayed: true`); a different body under the same key is 409 `idempotency_key_conflict`. |

**What the applicant sees.** The application detail carries the rejection (`rejection`: the stage and the reason) on the detail read only. The dashboard shows it ("Rejected by … This is final; a new application is needed to try again") and offers no edit link.

**What the officers see.** Every stage screen (IAME, Reviewer, Programme, and the shared Director and Secretary screen) has a "Reject permanently" panel under the return panel. Because it cannot be undone, the officer must write a reason **and** tick a confirmation; the screen sends nothing without both.

## What changed

- **Flyway V32:** `model_application_rejection` (append-only, one per application, a check limits it to the five working stages) and the disposable-cleanup function extended.
- **Spring:** `StageReject` (the five reject rules, beside `SliceAction` and `StageReturn`) and `gov.bee.api.rework` (`StageReject` controller, service, repository). No new error codes.
- **Contract 0.15.0:** the operation on both layers, `StageRejectRequest`, `StageRejectReceipt`, `ApplicationRejection` on the detail read.
- **A documentation defect, found and fixed.** Eight operations (IAME, Reviewer, Rating, Director, Secretary, Return, Resubmit and this one) carried the Finance fee-confirmation *summary* ("Confirm that the fee was received…"), because my clone scripts searched for a JSON-escaped arrow that never matched. The code, schemas, error tables and tests were right; only the human-readable summary was wrong, and it had been merged. All sixteen summaries are corrected, and two new tests in `contract-artifact.test.mjs` fail if two operations of a layer ever share a summary, or if a step's summary does not name the stage it starts from.
- The two checks that used `/reject` as a stand-in for a route that did not exist yet now use `/reject/override`.

## Limits

Tracked as BL-120 to BL-122 in [../BACKLOG.md](../BACKLOG.md): a rejected application can be appealed to nobody (no appeal or reopening path, as the spec says a new application is needed), the applicant is not notified, and the live check pauses the real officers' roles for its run.
