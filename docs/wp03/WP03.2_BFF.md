# WP03.2: browser-facing model-application reads (BFF)

Status: **WP03.2 BFF read activity implemented on branch `wp03.2-model-bff`, awaiting review. Not accepted. WP03 remains open; overall work-package count stays 1/11.**

Contract artifact: [`bee-local-api.openapi.json`](bee-local-api.openapi.json), contract version **0.3.0** (minor bump: two browser operations added, `ModelApplication` tightened to what Spring already emits, the idempotency contract recorded). The WP03.1 rules are unchanged: one `{error, message}` body, fixed messages, `X-Correlation-Id`, no-store, strict success validation and a per-operation status/code allowlist ([WP03.1_CONTRACT.md](WP03.1_CONTRACT.md)).

**What this is and is not.** The browser can now read model applications only through two same-origin Next.js routes. Next.js looks up the server-held `bee_session`, calls the existing Spring list/detail endpoints with that session's access token, validates Spring's answer and forwards it. Spring alone decides organisation, role, assignment and current-stage scope from `bee_app` rows. Next adds no scope rule, ID check, cache or redirect. No prototype screen consumes these routes yet: the UI read journey belongs to WP05.1. No write, approval, history read, route-policy grant, gateway or external service was added, and no screen-matrix proposal is a grant.

## Routes

| Browser route (Next :3100) | Spring call (:8090, internal) | Code |
| --- | --- | --- |
| GET `/api/runtime/model-applications` | GET `/api/model-applications` | `app/api/runtime/model-applications/route.ts` |
| GET `/api/runtime/model-applications/{id}` | GET `/api/model-applications/{id}` | `app/api/runtime/model-applications/[id]/route.ts` |
| GET `/api/runtime/me` (WP03.1, refactored onto the same helper) | GET `/api/me` | `app/api/runtime/me/route.ts` |

All three use `sessionRead` in `lib/server/bff.ts`, which does the following:
- Takes or issues the correlation ID.
- Resolves the session with `activeSession`, which refreshes tokens when needed.
- Calls Spring with the session token. The browser's `Authorization` header and query string are never forwarded.
- Passes Spring's status and body through `fromUpstream` with that operation's validator and error table (`SPRING_LIST` and `SPRING_READ` in `lib/server/apiContract.ts`).

POST, PUT, PATCH and DELETE on both routes return 405 `method_not_allowed` with `Allow: GET`. Paths with more segments, such as `/{id}/history` or `/{id}/submit`, fall to the JSON catch-all 404, which answers before any session lookup.

**ID segment.** The detail route forwards `{id}` to Spring unchanged when it is path-safe: 1 to 128 characters from `A-Z a-z 0-9 . _ ~ -`, excluding `.` and `..`. Anything else is sent as `-`, which Spring treats as an ordinary unknown ID after its own identity and scope checks. Next never decides that a record exists or doesn't. Sending `-` also keeps the Spring firewall's 400 (which an encoded slash would trigger) from making malformed IDs look different from unknown ones.

## Record mapping

The success bodies are Spring's, validated and forwarded byte-for-byte equivalent (the check compares the BFF and direct Spring JSON for every record).

| Field | Validation at the browser boundary |
| --- | --- |
| `ModelApplicationList` | exactly `authority`, `count`, `items`; `authority` is `spring-database`; `count === items.length`; every item is a valid `ModelApplication` |
| `id` | UUID |
| `reference`, `organisationCode`, `organisationName`, `modelName` | string |
| `state` | one of `draft`, `fee_due`, `iame_scrutiny`, `bee_scrutiny`, `rating`, `director_review`, `secretary_approval`, `approved`, `returned`, `rejected` |
| `version` | integer ≥ 0 (the persisted `model_application.version`) |
| `readBasis` | non-empty array of strings, each `own-org`, `assigned` or `stage:<state>` |

Any other key, at any depth, makes the whole response a 502.

## Error mapping

| Browser status / code | Cause |
| --- | --- |
| 401 `no_session` | No cookie, unknown or forged cookie (cleared), or only a bearer token |
| 401 `session_expired` | Keycloak refused the refresh; cookie cleared |
| 401 `unauthenticated` | Spring rejected the session's token |
| 403 `mfa_required`, `no_active_account`, `no_effective_role`, `no_read_scope` | Spring's documented refusals, forwarded with the contract message |
| 404 `not_found` (detail only) | Other organisation, unknown, malformed, unsafe segment, stale assignment, unassigned: one shape |
| 405 `method_not_allowed` | Any non-GET method |
| 502 `invalid_api_response` | 200 that fails the schema (extra field, wrong type, count mismatch) or a non-JSON body |
| 502 `api_error` | Status or code not in the operation's table, including SQL-like text in `error` or Spring 500 |
| 503 `api_unreachable` | Spring down; the portal session is kept |
| 503 `identity_unavailable` | Keycloak unreachable during refresh; the cookie is kept |
| 503 `service_unavailable` | Spring's own documented 503 |

Upstream text never reaches the browser. Every message comes from the fixed table, and the Next upstream log records only the correlation ID, path and status.

## Idempotency decision

**Recorded, not implemented.** Idempotency and 409 apply to write commands, and none exists. The contract is in the artifact's `x-bee-idempotency`. Building the store is deferred to the first reviewed write endpoint (WP05.1 create/edit/submit or WP07.1 fee). No table, cache or middleware was added. Summary:

- **Header.** `Idempotency-Key`, `^[A-Za-z0-9-]{16,64}$`, one per user intent and required on every write. Reads never take one.
- **Scope.** `bee_app` account + method + route template + target record ID.
- **Authorization first.** Spring re-checks identity and scope before any replay. A caller who has lost access gets the current denial.
- **Stored with the change, in one transaction.** The key scope, a SHA-256 of the canonical body, the response status and body, and the resulting record version are kept for 24 hours locally.
- **Replay.** The same key, scope and body returns the original answer with `Idempotency-Replayed: true`, with no second change or audit event.
- **Conflicts.** 409 `idempotency_key_conflict` (different body), 409 `idempotency_in_progress`, 409 `version_conflict` (stale `ModelApplication.version`, nothing stored). A missing key gives 422 `idempotency_key_required`.
- **Boundary.** Next validates the header syntax and forwards it. Spring owns the store and the decision.

Today the BFF routes answer every write method with 405 before any Spring call. The check proves this with an `Idempotency-Key` present, and no row changes.
