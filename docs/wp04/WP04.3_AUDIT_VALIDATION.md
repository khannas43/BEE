# WP04.3 — Scrutiny, validation and audit tests for WP04 (14 October 2026)

**Provisional local rules, not BEE rules.** This note is the evidence for the third sub-package of WP04. It follows the independent package review ([WP04_PACKAGE_REVIEW.md](WP04_PACKAGE_REVIEW.md)), which found that the audit and validation evidence was spread across the activity tests and that three things were missing or wrong. They are fixed here.

## What was added

| Part | What |
| --- | --- |
| Register audit trail (V47) | `register_status_event`, append-only (the same trigger as the other records). One row for every change of the register: a brand or an authorisation registered through an approved request (from nothing to active), revoked, closed on a date (status unchanged, `valid_to` before and after), and one row for each authorisation that goes with a revoked brand (`cascaded`). Each row names the actor, the time, the request or proposal behind it and the reason. The runtime login can read it; only the registration and revocation functions write it. `GET /api/register-revocations` returns the latest 50 as `events` (contract 0.31.0). |
| Name reuse (V47, V48) | A revoked brand's name can be registered again by the same owner: brand uniqueness is among live brands only, ignoring case and surrounding space (V47), and an approved request no longer blocks a new one for the same name or brand (V48). The new test found the second half: the first fix alone left the old approved request blocking the name. |
| Expired agency period (V47) | Approval refuses a request whose `valid_to` has already passed (BL-177). The answer is 422 `validation_failed` and nothing is written. |
| Consolidated test | `Wp04AuditValidationDatabaseTest` (3, real PostgreSQL, restricted runtime login): a registration's whole trail (filing, fee snapshot with the rule key and version, the three transitions with their actors and the approval note, the register entry), the immutability of every one of those records, the revocation with its cascade row by row, the audit trail readable through the API, name reuse, the half-open period boundaries (a period ending today is already over; starting today applies today), and a master supersession (closure with actor, reason and date; the earlier version unchanged and not editable). |

## What it shows against the exit criterion

"Draft-submit-review decisions and effective rules persist and are traceable": every decision (filing, fee confirmation, recommendation, approval, return, rejection, resubmission, revocation, closure, supersession of a master) is a row that names who and when and cannot be changed afterwards; the rule version used (fee rule key and version) is on the fee snapshot; the register's own changes are on `register_status_event`.

## Not covered (docs/BACKLOG.md)

BL-189 (a master closure names its actor as text, not a user id), BL-190 (organisation registration is not built), BL-188 (an agency can file for a brand it already holds), the BEE-dependent rules (BL-041, BL-161, BL-174).
