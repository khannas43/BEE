## Why one package

Five numbers are fixed in code today and each waits on a BEE answer. They are the same kind of thing as a fee rule (WP08.1a) or a rating scheme (WP08.1c): a value with a start date, changed by two people, never from the past, history kept. Doing them one at a time would add five more near-copies (BL-139). This package adds **one** generic setting mechanism and moves the five onto it.

## The mechanism

Same pattern as WP08.1a and WP08.1c.

| Rule | Behaviour |
| --- | --- |
| Where | `/app/administration/business-settings`, a menu entry that follows the permission (WP08.1d). |
| Who | A role holding the **permission** `business_setting_manage` (the Administrator now; another role later by a database row). Everyone else gets 403 `role_not_permitted`. |
| Propose | Pick a setting, enter a value (validated against that setting's type and range), a start date that is **today or later**, a source and a reason. |
| Approve or reject | A **different** permission holder; the proposer is refused (`segregation_refused`). Only the proposer may withdraw. |
| Take effect | Approval adds a new immutable version. The rule that applies is the version with the latest start on or before the day it is used (as for fee rules). If none exists the **seeded default** applies. |
| History | Versions are immutable; the screen shows the value in force, the next scheduled one, and the versions decided. Nothing already issued or recorded changes. |
| Which date | A rule is read at the moment of the action (submit, confirm, verify, issue), and the value used is stored on the record it affected, so a later change never re-explains an old decision. |

Each setting is a row in a small catalogue table (`business_setting_def`: key, label, unit, type, minimum, maximum, default, owner-assumption note), so a sixth setting is a seed row plus its enforcement point, not a new screen. The range limits in the catalogue are the guard: an Administrator cannot set the maximum efficiency above 100 or a negative tolerance.

## Open risks

- Changing `declared_iseer_max` or the maximum age affects drafts already saved; the rule is checked again at submit, so a saved draft can become unsubmittable. The catalogue carries a warning that the screen shows before approval (BL-156 for listing the affected drafts).
- A tolerance applies to money. The confirmation stores the amount actually received and the snapshot keeps the fee due, so finance can see every case where it was used; a finance view of those differences is not built.
- `iseer_verify_tolerance` defaults to 99.99, which means "no limit"; the label says so.
- The live check leaves probe versions (year 2100) because versions are immutable (BL-155).
