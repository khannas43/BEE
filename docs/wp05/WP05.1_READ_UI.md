# WP05.1a — Model application read-only UI

Status: **accepted as a narrow local read-only activity after review of `6afa301`.** WP05.1 and the WP05 package remain open. Work-package count stays **1/11**. Branch `wp05.1-read-ui`, rebased onto the reviewed WP04.2a tip `1c76ce4`; the rebase had no conflicts, and both the WP04.1 and the WP04.2a review records are intact in `DEVELOPMENT_PLAN.md`.

This increment wires the existing authenticated BFF reads into one manufacturer/agency screen. Spring alone decides organisation, role, assignment and stage scope. The browser never filters by organisation or role, never sends a bearer token, and never treats the development preview role as authority.

**What this is and is not.** A signed-in manufacturer or agency user can open `/app/model-label/model-dashboard` from a fresh browser profile, whatever the preview role, and can list and open detail for model applications the BFF returns. Detail is a contextual panel on the same route (`?id=`), loaded with a separate GET. No create, edit, submit, fee, rating or approval control is offered as operational. `/app/registrations/record` is not opened to Manufacturer. Spring permissions, the BFF and the screen matrix are unchanged; none of the 540 proposals is a grant. Writes, history, masters consumption and the rest of WP05.1 remain deferred.

| State | Behaviour |
| --- | --- |
| Loading | "Loading model applications…" / "Loading application…" |
| Empty list | "No model applications are available to you." |
| Session missing / expired / unauthenticated | Fixed BFF message; sign-in link; no record data |
| 403 (`no_read_scope`, MFA/account/role denials) | Fixed BFF message |

| Detail 404 | "No such record is available to you." — same copy whether the id is unknown or another organisation's |
| Selected row | `?id=<uuid>` opens the detail panel; Close clears the query |

| Signed out, session ended or role revoked while open | The screen revalidates the identity and both reads on window focus, tab visibility, a back-forward cache restore and every 30 s. The rows and detail are replaced by the BFF failure (`no_session`, `session_expired`, `no_effective_role`); a page restored from the back-forward cache is cleared before revalidating |

## Live evidence (real Keycloak, Next.js BFF and Spring; 1 October 2026)

`npm run local:read-ui` (`scripts/local/read-ui-browser-check.cjs`) drives headless Chrome through the DevTools Protocol. It reuses the sign-in and page helpers from `browser-check.cjs`, so no npm dependency is added. It signs in disposable twins of the personas with Keycloak password + TOTP; the seeded users are never used. The expected records come straight from `bee_app` (the organisation that owns each application), not from Spring, so the screen is compared with an independent source. Nothing is mocked:
- the loading states are made visible by delaying the network 1.5 s in DevTools;
- the outage is a real Spring stop and restart;
- the expired session is a real Keycloak admin logout, followed by waiting for the access token to expire.

Result: **26 passed, 0 failed**. Each persona signs in from a fresh Chrome profile with no `bee-role` in localStorage, so the preview role is the default (BEE Administrator). Twins were removed afterwards (`test-identities list`: none in Keycloak, 0 in bee_app).

### Runtime route (this revision)

`lib/runtimeRoutes.ts` lists the routes backed by the BEE service; today only the model dashboard. It records which Spring roles get a sidebar entry and which capabilities the screen really implements (List, View detail). It grants nothing: the BFF and Spring still decide every record.

- **Navigation.** `AppSidebar` adds the entry from `useSpringIdentity()` (Spring's `effectiveRoles`), not from the preview role.
- **Preview filter bypassed for this route only.** `RouteGuard` renders a runtime route without the "Not in this preview" deny screen and without the "Scoping is simulated" banner. `ScreenChrome` shows "Implemented here: List · View detail" instead of the preview access chips and skips the preview-role lock ("This screen is not available to the current role"). Every other route keeps the preview filter, banner and chips.
- **Banner.** The development preview banner stays (the preview role still drives the other screens) but says, on this route, that the records come from the BEE service and are scoped to the sign-in.
- **Identity freshness.** `refreshIdentity()` in `SessionBadge.tsx` re-reads `/api/runtime/me` and updates every subscriber, so the sidebar entry and the identity strip change together. Stale earlier identity responses are ignored.

The route is open to anyone in the browser, as it was to the matching preview roles before: with no session or no read scope it shows the BFF's fixed failure and no data.

### Defects fixed during live verification

1. **The screen was unreachable (404).** The original commit renamed the screen's catalogue title to "My model applications". Screen ids are slugs of the title, so the route became `/app/model-label/my-model-applications`. The menu link `/app/model-label/model-dashboard` and the `ModelDashboard` registration then pointed at a route that no longer existed. `npm run matrix` (5 violations) and `npm run audit:access` (1 violation) both report this, so those checks were evidently not run before that commit. The mocked tests could not see it. The catalogue title is restored to "Model dashboard", leaving `lib/screens.ts` identical to `1c76ce4`. The menu label stays "My model applications".
2. **Endless loading on a network failure.** If `fetch` itself rejected, the promise was unhandled and the screen stayed on "Loading…". Both reads now return the unreachable failure, and a unit test covers it.

## Remaining gaps

- **Revalidation is client-side polling.** A revoked role or ended session clears the screen on the next focus, tab show, back-forward restore or 30 s tick, not instantly. Previously displayed rows can remain during an in-flight revalidation until its response arrives. Each new read is checked by Spring.
- **Preview banner still present.** The development preview banner and role switcher remain on this route because they drive the rest of the prototype; the banner text says this screen uses BEE service data.
- **Not covered live:** the `mfa_required` and `no_active_account` states on this screen (covered by the BFF checks and the mocked tests); pagination or large lists (4 seeded rows); keyboard and screen-reader review; Hindi copy for the new strings.
- `local:read-ui` is not part of `local:check`, because it stops Spring and waits for token expiry (about 90 s). Run it separately.
- Writes, history, masters consumption (WP04.1) and brand authorisation (WP04.2a) are not used by this screen; the rest of WP05.1 is deferred.
