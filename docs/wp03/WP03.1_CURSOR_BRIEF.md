# WP03.1 Cursor brief — API contract and error standards

Status: next activity brief, not implementation or acceptance. Baseline: create a branch from the commit containing this brief on `wp02.3-local-mfa` (its reviewed parent is `bafae63`); verify a clean tree first. WP01 is 1/11 accepted; WP02 and WP03 remain open.

## Scope and architecture

Use the existing same-origin Next.js server routes as the browser-facing boundary and the single Spring Boot API as the authority. Do not install a separate API gateway, APISIX or a new service on this MacBook. ADR-001 D-RT2 and DEVELOPMENT_PLAN §3.2 govern this local scope.

WP03.1 owns a versioned, reviewable contract for the routes already implemented: Spring GET `/api/me`, `/api/model-applications`, `/api/model-applications/{id}`, the minimal health endpoint, and Next.js `/api/runtime/me` plus the auth/session routes where they are part of this boundary. Document which routes are internal and which are browser-facing. Version the contract artifact without silently adding `/v1` route aliases or widening the Spring security matchers.

Create an OpenAPI artifact with concrete schemas, examples, status codes and error codes for the current endpoints. It must describe the Spring database authority and scope, MFA requirement, no browser bearer token, no-store responses, and that out-of-scope, unknown and malformed model IDs have indistinguishable 404 response shape. Do not claim unimplemented create/edit/transition/history routes as operational; list them as deferred contracts with owners if useful.

Define one small error contract that preserves the existing stable `error` code consumed by checks. Include correlation ID in a response header, safe client message or detail if needed, and clear 401/403/404/409/422/502/503 semantics for future work. Avoid leaking record existence, tokens, stack traces, SQL or Keycloak internals. Resolve current Spring Security, controller and Next BFF error inconsistencies without changing who can read or act.

Keep `X-Correlation-Id` generated or validated at the Next boundary and propagated to Spring, with the same value returned on success and denial; reject or replace unsafe incoming values. No correlation ID value should be an authorization input. Document how it is logged locally without sensitive data.

## Checks and boundaries

- Add contract checks that compare the OpenAPI artifact with live Spring and Next.js responses for a valid Nova read, cross-organisation/unknown/malformed read, no token, missing MFA, inactive role, denied write, upstream unavailable, and correlation propagation. A current/unknown/malformed record must not disclose which case occurred.
- Inspect current checks before adding tests; use focused behavioral cross-layer checks rather than a large generated test suite that only repeats the schema.
- Preserve Keycloak TOTP, all 16 seeded accounts and their sessions, the disposable-test-identity guard, the 540 ungranted matrix proposals, and default-deny writes. Routine `local:check` must stay non-destructive to protected identities.
- Do not implement model list/detail BFF routes or business UI in WP03.1 unless needed to prove this existing contract; those belong to WP03.2. Do not change the URL policy, enable workflow endpoints or present a separate gateway as installed.
- Run focused contract checks, Spring/Web tests, `local:check`, matrix, access audit, typecheck, changed-file lint and build. Report the old whole-repository lint baseline separately. Do not replay destructive RT1. Stop runtime after verification.
