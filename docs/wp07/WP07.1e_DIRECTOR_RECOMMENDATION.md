# WP07.1e — The Director reviews the rating and recommends (first slice step 6)

**Status:** Implemented locally on branch `wp07.1e-director`; local checks pass (see Evidence). **Not independently reviewed or accepted.** WP05.2 and the first slice remain open; the work-package count stays 1/11.

**Provisional local rules, not BEE rules, and one owner assumption.** Decision D1 asks whether Secretary approval is always required. The owner had no answer and chose to assume, on 4 October 2026, that **the Director's recommendation can be final for some categories**. That is an assumption of this build, not a BEE rule. It is data, not code: the append-only table `director_final_rule` says which categories (the latest row that has started wins; a change is a new row). The only seeded rule is `RAC = not final`, so the Secretary step stays in the chain and is still exercised end to end. Nothing is final until a rule row says so.

## What it does

`POST /api/model-applications/{id}/director-recommendation` (browser route `/api/runtime/model-applications/{id}/director-recommendation`) moves an application from `director_review` to `secretary_approval`, or straight to `approved` where the recommendation is final for the category. The screen is `/app/model-label/director-approval`, in the sidebar for a Director identity only.

| Rule | Behaviour |
| --- | --- |
| Who | The reviewed slice rule `SliceAction.DIRECTOR_RECOMMEND` through `SlicePolicy.check`: a Director role with scope `all`, the `director_review` source state, and nobody who already acted at another stage. Another role gets 403 `role_not_permitted`. |
| What the Director sees | Only applications in the `director_review` stage. An application that has moved on is the same 404 `not_found` as an unknown one. |
| The rating | The application detail read now carries the latest rating once there is one (`rating`: stars, the declared and the verified figure, scheme, rating version). It is on the detail read only, not the list. It is a local demonstration rating, always marked `localDemoRating: true`. |
| Separation | A caller from the application's own organisation, or who took an earlier step (Finance, the IAME officer, the Reviewer, Programme), gets 403 `segregation_refused`. |
| Input | `version` and `note` (1 to 500 characters after trimming, no control characters). |
| The outcome | `directorFinal` is read from `director_final_rule` for the application's category on today's India date; no rule that has started means not final (fail safe). Final goes to `approved`, otherwise to `secretary_approval`. The receipt says which, and a database check and the validator both refuse a final flag that disagrees with the state. |
| Atomic write | One transaction: the guarded state change, an append-only `model_application_transition_event`, and an append-only `model_application_director_recommendation`. |
| Next stage | No officer is assigned: the Secretary reads the `secretary_approval` stage by role. |
| Idempotency | A key is required. A repeat with the same body returns the stored **receipt** (header `Idempotency-Replayed: true`); a different body under the same key is 409 `idempotency_key_conflict`. |

## What changed

- **Flyway V29:** `director_final_rule` (append-only, RAC not final), `model_application_director_recommendation` (append-only; a check ties `director_final` to the resulting state) and the disposable-cleanup function extended.
- **Spring:** `gov.bee.api.director` (controller, service, repository); the detail read attaches the latest rating (`ModelApplicationSubmitRepository.findLatestRating`). No new error codes.
- **Contract 0.11.0:** the operation on both layers, `DirectorRecommendationRequest` and `DirectorRecommendationReceipt`, the optional `rating` on `ModelApplication` (`ApplicationRating`), and `lib/server/contracts/director-recommendation.ts`.
- **Screen:** `DirectorApproval` on the kit, showing the rating (stars, declared and verified figures, "not a BEE rating"), the evidence and the test reports.
- **Tooling:** the shared browser helper's temp-profile cleanup could fail a check with `ENOTEMPTY` when Chrome's helper processes were still writing; it is now best-effort (more retries, never fails a check).

## Limits

Tracked as BL-108 to BL-111 in [../BACKLOG.md](../BACKLOG.md). The main one: the **final-for-the-category path is proven by the database and contract tests but not live**, because RAC is the only category, it is seeded as not final, and the rule table is append-only, so a live check cannot flip it and clean up.
