# WP02.3 Local TOTP, delegation rules and denial rechecks

Status: **WP02.3 local TOTP implemented and checked on 30 September 2026; awaiting review. WP02 remains open and is not accepted.** Delegation is documented as candidate rules only (§6); nothing grants delegated access. Work-package count stays 1/11.

Brief: [WP02.3_CURSOR_BRIEF.md](WP02.3_CURSOR_BRIEF.md). Earlier activities: WP02.1 sign-in and session, [WP02.2_POLICY.md](WP02.2_POLICY.md) list/read policy.

## 1. Policy

Every interactive sign-in to the portal needs the account password **and** a time-based one-time code (TOTP, RFC 6238) from an authenticator app. It applies to all 16 seeded Keycloak users; no role, organisation or client is exempt. There is no SMS, email or external OTP service, and no recovery codes.

| Layer | Rule | Where |
| --- | --- | --- |
| Keycloak browser flow | `bee browser with otp`: cookie (existing SSO) **or** username/password form REQUIRED then OTP form REQUIRED. A user without an OTP credential is forced through `CONFIGURE_TOTP` before any code is issued. | `local/generate-fixtures.cjs` → `local/keycloak/import/bee-local-realm.json` |
| Keycloak direct grant | `bee direct grant with otp`: username, password and OTP all REQUIRED. The local check client cannot get a token with a password alone. | same |
| OTP policy | TOTP, HmacSHA1, 6 digits, 30 s, look-around 1 step, **a code cannot be reused** (`otpPolicyCodeReusable: false`). | same |
| Seeded users | Every user starts with required action `CONFIGURE_TOTP` and no OTP credential. | same |
| Token evidence | Protocol mapper `amr` on `bee-web` and `bee-local-check`; the password and OTP steps record `pwd` and `otp`. | same |
| Portal callback | After the state, issuer, code exchange (PKCE) and ID-token checks, the ID token's `amr` must contain `pwd` and `otp`; otherwise the Keycloak session is ended and the callback fails with `mfa_required`. No session is created. | `app/api/auth/callback/route.ts`, `lib/server/oidc.ts` (`meetsMfaPolicy`) |
| Server session | Records the verified `authMethods`; shown (no tokens) by `GET /api/auth/session`. | `lib/server/session.ts` |
| Spring | Before any database lookup, an access token whose `amr` lacks `pwd` or `otp` gets 403 `mfa_required` on `/api/me` and every model-application route. The database authorization of WP02.2 is unchanged and still decides. | `backend/.../identity/MfaPolicy.java`, `CallerResolver.java`, `MeController.java` |

The portal and Spring checks are defence in depth: they hold even if the realm is misconfigured. `mfa.portal-refuses-password-only` and `mfa.spring-refuses-password-only` prove this by temporarily binding the built-in conditional flows, which let a user without OTP sign in with a password only, then restoring them.

**First sign-in after enrollment.** Keycloak verifies the setup code as a required action, not through the OTP step, so the ID token from the enrolling login carries `amr: ["pwd"]`. The portal refuses it (`mfa_required`, message: "If you have just set up your authenticator, sign in again and enter a new code"), ends that Keycloak session, and the user signs in again with password and a fresh code. This keeps the rule simple (a session exists only for a token that records a verified OTP step) at the cost of one extra sign-in. It is checked by `mfa.<user>.enrolled` and `mfa.<user>.first-otp-sign-in`.

## 2. Evidence (automated)

`npm run local:mfa` (`scripts/local/mfa-check.cjs`, about 1.5 minutes; it waits for unused 30-second steps) drives the real portal routes and Keycloak pages over HTTP. It is part of `npm run local:check`. For Nova and PixelCert it first removes the user's OTP credential, the same state as a fresh identity reset.

| Check | Shows |
| --- | --- |
| `mfa.realm-policy`, `mfa.every-user-covered` | flow bindings, REQUIRED OTP steps, non-reusable codes; every one of the 16 users is enrolled or has `CONFIGURE_TOTP` pending |
| `mfa.<u>.enrollment-required` | after the password, Keycloak shows TOTP setup (PKCE S256, state, nonce sent); no portal cookie; `/api/auth/session` unauthenticated |
| `mfa.<u>.enroll-missing-code`, `…enroll-wrong-code` | setup refuses an empty and a wrong code; no session |
| `mfa.<u>.enrolled`, `…first-otp-sign-in` | correct setup code stores one OTP credential; that login is refused with `mfa_required`; the next login asks for password then OTP (not setup); a code gives `/app`, session `authMethods ["pwd","otp"]`, Spring `/api/me` 200 with the right organisation |
| `mfa.<u>.logout`, `…fresh-challenge` | logout ends the portal session and the Keycloak session; the next login shows the login form, then the OTP challenge |
| `mfa.<u>.missing-otp`, `…wrong-otp`, `…correct-otp` | empty and wrong codes are refused with no session; a correct code then succeeds |
| `mfa.<u>.replayed-otp`, `…after-replay` | the code from the previous login, still inside its time window, is refused; a new code is accepted |
| `mfa.password-grant` | check client: no code 400, wrong 400, correct 200 with `amr ["pwd","otp"]`, same code again 400 |
| `mfa.rejected-callback-*` | §5 |
| `mfa.spring-denied-retry` | `no.account` passes password and OTP, Spring refuses (`no_active_account`), the Keycloak session is ended, and a retry asks for password and OTP again |
| `mfa.portal-refuses-password-only`, `mfa.spring-refuses-password-only`, `mfa.realm-restored` | defence in depth (§1) |

Other updated checks: `auth-check.cjs` (31), `browser-check.cjs` (23, real Chrome fills the OTP challenge; the login page lists TOTP as an implemented control) and `access-check.cjs` all sign in with TOTP; `oidc.test.mjs` adds the `amr` policy test (17); Spring adds `tokenWithoutOtpIsRefusedBeforeAnyDatabaseLookup` and `passwordOnlyTokenIsRefusedBeforeAnyDatabaseLookup` (64 tests).

**Test authenticator.** `scripts/local/totp.cjs` enrolls through Keycloak's real setup page and keeps the Keycloak-generated secret in git-ignored `.local/run/totp/<user>.json` (directory 0700, files 0600). Nothing reusable is committed. It hands out each 30-second step once per user because Keycloak refuses reuse. If the stored secret no longer matches the user's credential (for example after an identity reset), it removes the credential and enrolls again. No disposable Keycloak users are created; the only temporary realm change (flow binding) is restored in `finally`.

## 3. Repeatable manual sequence

Needs an authenticator app (any RFC 6238 app; on the Mac, `oathtool --totp -b <key>` also works if installed). Manual-only evidence: scanning the QR code with a real phone app, and how the Keycloak pages look in a normal browser. Everything else below is also covered automatically in §2.

1. `npm run local:up`, then `npm run local:reset:identity` (Keycloak only; `bee_app` untouched). Optional: `node scripts/local/mfa-check.cjs --realm-only` shows 16 users with `CONFIGURE_TOTP` pending and 0 enrolled.
2. Open http://127.0.0.1:3100/login in a private window, choose **Sign in with BEE identity**, sign in as `nova.applicant` / `bee-local-dev`.
3. Keycloak shows **Mobile Authenticator Setup**. Submit with the code empty: "Please specify authenticator code." Submit `000000`: "Invalid authenticator code." (if `000000` happens to be valid, use any other wrong code).
4. Scan the QR code (or choose "Unable to scan?" and enter the key), enter the app's code, submit. The portal shows the sign-in page with "If you have just set up your authenticator, sign in again and enter a new code." There is no session (http://127.0.0.1:3100/api/auth/session shows `"authenticated":false`).
5. Sign in again: password, then the **one-time code** page. Submit empty, then a wrong code: both refused. Enter the current code: you reach `/app` as Nova Cool, and `/api/auth/session` shows `"authMethods":["pwd","otp"]`.
6. Sign out. Sign in again: Keycloak asks for the password and then a code (not setup). Re-entering the code you just used, within the same 30 seconds, is refused; wait for the next code.
7. Optionally repeat as `pixel.applicant`, and as `no.account` (OTP accepted, then "no active BEE portal account"; the next attempt asks for password and code again).

## 4. Identity reset and recovery (local)

- `npm run local:reset` stays application-only: it reloads `bee_app` and restarts the API; Keycloak users and OTP credentials are untouched (checked: enrolled count unchanged after `local:reset`).
- `npm run local:reset:identity` re-imports the realm: all users lose their OTP credential and get `CONFIGURE_TOTP` again; `bee_app` is not touched. Local secret files become stale and `totp.cjs` re-enrolls when the checks next run; delete `.local/run/totp/` to discard them.
- One user lost their authenticator: Keycloak admin console http://127.0.0.1:8180/admin (local admin), realm `bee-local` → Users → user → Credentials → delete the OTP credential, then sign the user out (Sessions). Because the OTP step is REQUIRED, the next login forces enrollment (`mfa.<u>.enrollment-required` starts from exactly this state). Equivalent script: `removeOtp` in `scripts/local/totp.cjs`.
- There is no self-service recovery, no recovery codes and no identity-proofing step. Production recovery is out of scope for this local demonstration.

## 5. Rejected callbacks, retry and logout

A callback the portal rejects **after** Keycloak authenticated the user (tampered state, `mfa.rejected-callback-leaves-kc`) leaves that browser's Keycloak session in place; the portal has no tokens for it and cannot end it. A retry in the same browser (`mfa.rejected-callback-retry`) reuses that session without a new password or code; the new ID token still records the original `pwd` and `otp`, so the MFA rule holds. Portal logout then ends it, and the next login asks for password and code again (`mfa.rejected-callback-logout`). Closing the browser or Keycloak's SSO idle timeout also ends it.

When Spring refuses an identity (`no_active_account`, `no_effective_role`) or the MFA rule fails, the portal does have the tokens and ends the Keycloak session at once (`auth.denied.*`, `mfa.spring-denied-retry`, `mfa.portal-refuses-password-only`).

Not claimed: portal logout does not end the user's other Keycloak sessions (another browser, the account console), and Spring accepts an already-issued access token until it expires (5 minutes).

## 6. Delegation: candidate rules (not implemented)

No delegation record, endpoint or policy exists. `CallerResolver` and `SlicePolicy` ignore any notion of delegation, so nobody acts for anyone else. These are candidate rules for review; they decide nothing and grant none of the 540 screen-matrix proposals. Provisional decision D1 ([FIRST_SLICE.md](../wp01/FIRST_SLICE.md) §10) stands: Secretary final approval is always required and is not delegable unless the Secretary's final decision on D1 says otherwise.

| Topic | Candidate rule |
| --- | --- |
| Grant | Only through an explicit `delegation` record in Spring's database (delegator, delegate, role, scope such as category/stage/organisation, reason, `valid_from`, `valid_to`). A Keycloak role or group change is never a delegation. The delegate gets no more than the delegator holds, in the same scope; no re-delegation; never Secretary final approval (D1). |
| Eligibility | The delegate needs an active account, an active role assignment of their own, the same organisation where the role is organisation-bound, and an MFA session. Segregation of duties (N8) still applies to the delegate for each application. |
| Maker-checker | A delegation takes effect only when a second authorised person approves it. Maker, checker and delegate are three different users; nobody approves a delegation to themselves. |
| Expiry | `valid_to` is mandatory and short (for example, at most 30 days; to be decided); no open-ended delegation. Checked on every request against server time. |
| Revocation | The delegator or an authorised administrator can revoke at any time, effective on the next request (no cached grant). Actions already taken are not reversed. Revoked and expired records are kept. |
| Audit | Append-only events for requested, approved, rejected, used, expired and revoked. Every action taken under a delegation records the acting user, the delegator and the delegation id, with server time. |

## 9. Gaps

- One extra sign-in after enrollment (§1).
- Keycloak brute-force detection is not enabled in the local realm, so OTP and password guesses are not rate-limited. To be decided before any wider use.
- No recovery codes, no self-service authenticator reset, no step-up for sensitive actions, no remembered devices.
- In-memory portal sessions and HTTP cookies remain local-runtime limits (WP02.1).
- Within a live Keycloak browser session a new portal login reuses SSO without a new code (§5); no universal session revocation.
- Seeded users share the documented local password `bee-local-dev` (unchanged).
- Delegation is documented only (§6); escalation (R12) is not started; N1 edit, N6, N8 and full A7 remain pending.
