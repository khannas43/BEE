# WP03.1: local API contract, errors and correlation

Contract artifact: [`bee-local-api.openapi.json`](bee-local-api.openapi.json) (OpenAPI 3.1, contract version **0.2.0**). This file is the evidence and explanation for review; it does not accept WP03 or any work package.

**Architecture.** The Next.js same-origin route handlers are the only browser-facing boundary, and the single Spring API is the authority (ADR-001 D-RT2, DEVELOPMENT_PLAN §3.2). There is no separate gateway: the plan row "Gateway and OpenAPI/error standards" is met by that boundary, not by an installed gateway, APISIX or new service. Spring listens on 127.0.0.1 and is called only by Next.js server code with the session's access token.

The artifact also states:
- **Database authority and scope.** Spring decides every read from `bee_app` account, membership, role and assignment rows. A token's organisation claim is echoed under `ignoredTokenClaims` and never used.
- **MFA.** `amr` must contain `pwd` and `otp`.
- **No browser token.** The browser holds only the opaque `bee_session` cookie, and a browser `Authorization` header is ignored.
- **No-store.** Every response of both layers carries it. Spring sends `no-cache, no-store, max-age=0, must-revalidate`; Next sends `no-store`.
- **One 404.** Out-of-scope, unknown, malformed and stale-assignment model IDs return the same 404.

## Error contract

One body for both layers: `{"error": "<code>", "message": "<fixed safe text>"}`. Nothing else is in the body, so the stable `error` code consumed by existing checks is unchanged. The correlation ID is carried in the `X-Correlation-Id` header, never in the body. Messages are fixed per code (`ApiErrors.java`, `lib/server/apiContract.ts` and `x-bee-error-codes` in the artifact; the unit tests fail if the three disagree). A message never includes a record ID, token, SQL, stack trace or Keycloak detail.

| Status | Code | Layer | When |
| --- | --- | --- | --- |
| 401 | `unauthenticated` | Spring | Missing, expired or invalid bearer token |
| 401 | `no_session` | Next | No, unknown or forged session cookie; a browser bearer token is ignored |
| 401 | `session_expired` | Next | Session ended or refresh refused; cookie cleared |
| 403 | `mfa_required` | Spring | Token `amr` lacks `pwd`+`otp` |
| 403 | `no_active_account` | Spring | No active `bee_app` account for the subject |
| 403 | `no_effective_role` | Spring | No database role that is active, in date and in the token |
| 403 | `no_read_scope` | Spring | Role has no model-application read rule |
| 403 | `denied_by_default` | Spring | Any unmapped method/path with a valid token (all writes, history, other actuator endpoints) |
| 403 | `cross_origin` | Next | Logout without the portal Origin |
| 404 | `not_found` | both | Record not available to this caller (does not reveal whether it exists); unmatched `/api` path |
| 405 | `method_not_allowed` | Next | Unsupported method; `Allow` header lists the method |
| 409 | — | reserved | Stale version or duplicate idempotency key on future writes (WP03.2/WP05) |
| 422 | — | reserved | Invalid write input (WP05.1) |
| 500 | `internal_error` | Spring only | Unexpected failure; logged by exception class with the correlation ID; mapped to 502 `api_error` at the browser boundary |
| 502 | `invalid_api_response`, `api_error` | Next | Spring answered with non-JSON or a status/code pair outside this contract |
| 503 | `service_unavailable` | Spring | Database failure during an allowed request |
| 503 | `api_unreachable`, `identity_unavailable` | Next | Spring or Keycloak unreachable; session kept; retry later |

**Inconsistencies resolved.** Who can read or act is unchanged: the `SecurityConfig` matchers and `SlicePolicy` are untouched, and `contract.inventory` asserts the five matchers.
- **Error bodies.** Spring Security handlers, the two controllers and the Next routes each built their own `{error}` body. All now share one helper per layer (`ApiErrors`, `errorBody`).
- **Upstream outage.** "Spring unreachable" was 502. It is now 503 `api_unreachable`, because the dependency is unavailable rather than misbehaving. The callback now tests the error code instead of the status.
- **Error passthrough.** Next forwarded Spring's status and body verbatim, so a Spring 500 or an unknown code would have reached the browser. It now passes successes and known denials through, and maps everything else to 502 `api_error`.
- **Success passthrough (0.2.0).** A 200 from Spring `/api/me` was forwarded whatever it contained. `validateMe` in `lib/server/apiContract.ts` now checks it against the `Me` schema strictly, before `/api/runtime/me` forwards it or the callback creates a session: required fields, types, and no undocumented field at any level. `ignoredTokenClaims` is now closed to `{organisation}` in the artifact too. A body that fails gets the fixed 502 `invalid_api_response`, and nothing from it is forwarded.
- **Callback redirect codes (0.2.0).** The callback copied Spring's `error` string into `/login?error=`, so any upstream text would reach the URL. `callbackOutcome` now accepts only the status/code pairs documented for `springMe` (`SPRING_ME_ERRORS`). A 200 that is not exactly `Me` becomes `invalid_api_response`, anything else becomes `api_error`, and `safeLoginCode` limits every redirect to `x-bee-login-redirect-codes`. The login page has messages for the new codes.
- **Database failure.** It fell through to Spring's `/error`, which default deny turned into a misleading 401/403. A `@RestControllerAdvice` now returns 503 `service_unavailable`, or 500 `internal_error` for anything unexpected.
- **Unmatched paths.** Unmatched Spring GETs under an allowed prefix give the same 404 body. Unmatched portal `/api` paths return the JSON 404 instead of the HTML page.
- **Unsupported methods.** These got Next's empty automatic 405. They now get the contract body.
- **Charset.** Security-handler errors declared ISO-8859-1. They now declare UTF-8.

## Correlation IDs

- **Rule (both layers).** An incoming `X-Correlation-Id` matching `^[A-Za-z0-9-]{1,64}$` is kept. Anything else, including a missing value, is replaced by a new UUID.
- **Next.** Every browser-facing route accepts or issues the ID, sends it to Spring on the upstream call, and returns the same value on success, denial, redirect and outage. Before WP03.1, the Next routes ignored the incoming value, and the auth routes returned no header.
- **Spring.** `CorrelationIdFilter`, which runs first, applies the same rule for direct callers and sets the header before security runs, so 401 and 403 responses carry it too.
- **Not for authorization.** The ID is never an authorization input. No code reads it except to echo and log it.
- **Logging.** Spring writes one `bee.access` line per request: `correlationId`, `method`, `path` (query string dropped, unsafe characters replaced, 120 characters at most), `status` and `durationMs`. The ID is also in the MDC for any other line in the request. Next writes one `bee.upstream` line per Spring call: `correlationId`, Spring path, status, known error code and duration. Neither layer logs headers, tokens, cookies or bodies.
- **Callback URL.** `next.config.ts` drops `/api/auth/callback` from the `next dev` request log, because its query holds the one-time authorization code and state, which the earlier `web.log` contained.
- **Where.** The logs are `.local/logs/api.log` and `.local/logs/web.log`, both git-ignored.

## Version policy

`info.version` is the contract version (semantic versioning):
- **Patch:** wording or examples.
- **Minor:** a new optional field, route or error code.
- **Major:** a removed or renamed field, or a changed status or code meaning.

URL paths are not versioned. There are no `/v1` aliases while the API is local-only, and the Spring matchers were not widened. A change to routes, codes or messages must update the artifact in the same commit, or `web:test` and `local:contract` fail.

## Gaps and remaining work

- **WP03.2:**
  - the browser-facing model list/detail BFF routes (currently 404 at the catch-all) and their contract operations;
  - idempotency keys and the reserved 409;
  - the shared persisted record seen through browser and API.
- **WP03.3:**
  - generated client or server stubs, if wanted;
  - a full contract test suite beyond these focused behavioural checks;
  - structured (JSON) log output, log retention and correlation across Keycloak events;
  - checking response headers for every documented status rather than the ones exercised here.
- **Not proven live:**
  - Spring 503 `service_unavailable` on a database outage. It is proven only in MockMvc, because stopping the shared Postgres container would also stop Keycloak;
  - Next 503 `identity_unavailable`;
  - Next 502 for non-JSON Spring bodies, which is proven in unit tests only. The schema and unknown-code 502s are proven live with the stand-in.
- **Enforcement scope.** Only `/api/me` reaches the browser from Spring today. When WP03.2 adds the model BFF routes, each needs its own validator and error table, using the same `fromUpstream` pattern.
- **Missing MFA at the browser boundary.** It is refused at the callback, so no session ever reaches `/api/runtime/me` without `otp`. The Spring check uses a token that lacks `amr` rather than a password-only login, because the realm's direct grant requires OTP.
- **Contract format.** The artifact is JSON rather than YAML, because `js-yaml` and `ajv` are only transitive dependencies, and the validator is a deliberate small subset. Swagger UI and other viewers are not installed.
- **Log content.** Spring's default Boot startup lines and Next's dev request log (paths with query strings other than the callback, for example `returnTo`) still appear in the local logs. They contain no tokens.
