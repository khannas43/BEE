# WP05.1a — Model application read-only UI

Status: **implemented and verified live locally; awaiting review, not accepted.** WP05.1 and the WP05 package remain open. Work-package count stays **1/11**. Branch `wp05.1-read-ui`, rebased onto the reviewed WP04.2a tip `1c76ce4`; the rebase had no conflicts, and both the WP04.1 and the WP04.2a review records are intact in `DEVELOPMENT_PLAN.md`.

This increment wires the existing authenticated BFF reads into one manufacturer/agency screen. Spring alone decides organisation, role, assignment and stage scope. The browser never filters by organisation or role, never sends a bearer token, and never treats the development preview role as authority.

**What this is and is not.** Partners already allowed to open `/app/model-label/model-dashboard` can list and open detail for model applications the BFF returns. Detail is a contextual panel on the same route (`?id=`), loaded with a separate GET. No create, edit, submit, fee, rating or approval control is offered as operational. `/app/registrations/record` is not opened to Manufacturer. Route policy and the screen matrix are unchanged; none of the 540 proposals is a grant. Writes, history, masters consumption and the rest of WP05.1 remain deferred.

## UI states

| State | Behaviour |
| --- | --- |
| Loading | "Loading model applications…" / "Loading application…" |
| Empty list | "No model applications are available to you." |
| Session missing / expired / unauthenticated | Fixed BFF message; sign-in link; no record data |
| 403 (`no_read_scope`, MFA/account/role denials) | Fixed BFF message |
| BFF or Spring unreachable | "The BEE service is not reachable. Try again later." on list and detail; no rows or stale data. A request that never reaches the BFF (network failure) shows the same message instead of loading forever |
| Detail 404 | "No such record is available to you." — same copy whether the id is unknown or another organisation's |
| Selected row | `?id=<uuid>` opens the detail panel; Close clears the query |

## Live evidence (real Keycloak, Next.js BFF and Spring; 1 October 2026)

`npm run local:read-ui` (`scripts/local/read-ui-browser-check.cjs`) drives headless Chrome through the DevTools Protocol. It reuses the sign-in and page helpers from `browser-check.cjs`, so no npm dependency is added. It signs in disposable twins of the personas with Keycloak password + TOTP; the seeded users are never used. The expected records come straight from `bee_app` (the organisation that owns each application), not from Spring, so the screen is compared with an independent source. Nothing is mocked:
- the loading states are made visible by delaying the network 1.5 s in DevTools;
- the outage is a real Spring stop and restart;
- the expired session is a real Keycloak admin logout, followed by waiting for the access token to expire.

Result: **21 passed, 0 failed**. Twins were removed afterwards (`test-identities list`: none in Keycloak, 0 in bee_app).

The prototype only *displays* this screen when the development preview role is manufacturer or agency. That is the existing `RouteGuard` display filter, not an access decision. The live check therefore selects that preview role to make the screen visible. It shows the preview never changes the data: other personas previewing as manufacturer still get Spring's empty and forbidden answers. No route, permission or filter was changed.

### Defects fixed during live verification

1. **The screen was unreachable (404).** The original commit renamed the screen's catalogue title to "My model applications". Screen ids are slugs of the title, so the route became `/app/model-label/my-model-applications`. The menu link `/app/model-label/model-dashboard` and the `ModelDashboard` registration then pointed at a route that no longer existed. `npm run matrix` (5 violations) and `npm run audit:access` (1 violation) both report this, so those checks were evidently not run before that commit. The mocked tests could not see it. The catalogue title is restored to "Model dashboard", leaving `lib/screens.ts` identical to `1c76ce4`. The menu label stays "My model applications".
2. **Endless loading on a network failure.** If `fetch` itself rejected, the promise was unhandled and the screen stayed on "Loading…". Both reads now return the unreachable failure, and a unit test covers it.

## Remaining gaps

- **Screen visibility depends on the preview filter.** A signed-in manufacturer or agency user whose preview role is something else (the fresh-profile default is Administrator) sees "Not in this preview" instead of their records. The fix is to drive this route's visibility from the Spring identity rather than the preview role. That is a route-policy change, left for review (WP02 / WP05.1).
- **Misleading prototype chrome on this screen.** The external-role banner says "Scoping is simulated here with sample data". The "Your access" chips come from the preview role's catalogue cells (for example "D · Download or export"). Neither is true of this screen's data, and no download exists. The shared components are unchanged here.
- **Not covered live:** the `mfa_required`, `no_active_account` and `no_effective_role` states on this screen (covered by the BFF checks and the mocked tests); pagination or large lists (4 seeded rows); keyboard and screen-reader review; Hindi copy for the new strings.
- `local:read-ui` is not part of `local:check`, because it stops Spring and waits for token expiry (about 90 s). Run it separately.
- Writes, history, masters consumption (WP04.1) and brand authorisation (WP04.2a) are not used by this screen; the rest of WP05.1 is deferred.
