# WP04.1 — Effective-dated masters (local foundation)

Status: **implemented locally, awaiting review.** WP04 is not accepted and the work-package count stays **1/11**. Branch `wp04.1-masters`, from `0c97af6`.

This activity persists five internal masters: appliance categories, applicable standards, laboratory accreditation, fee rules and rating-formula metadata. Every row records its source, verification status, version and effective period. Spring can resolve the version that applies on a given date. No browser screen, API route, permission, administration write, model submission, fee confirmation or rating computation uses these masters yet. WP04.2 owns the organisation, agency and brand workflows. WP05.1 (submission: category, standard, accreditation and fee) and WP05.2 (rating) will consume these rules when they build those actions.

**Nothing here is BEE-approved.** Every seeded row is `synthetic` or `provisional`, and none is `verified`. The fee amounts and the placeholder rating formula must not be shown as official, and no star rating is computed.

## 1. Schema (`V4__effective_dated_masters.sql`)

Each master has its own table in schema `app`. All five share these columns:

| Column | Meaning |
| --- | --- |
| `id` | uuid, generated |
| `rule_key` | The key that versions are compared within (below) |
| `version` | Positive integer; `UNIQUE (rule_key, version)` |
| `effective_from` | First calendar date the version applies (inclusive) |
| `effective_to` | First calendar date it no longer applies (exclusive); `NULL` means open-ended; must be later than `effective_from` |
| `source_reference` | Where the value came from; must not be empty |
| `verification_status` | `synthetic`, `provisional` or `verified` |
| `note`, `legacy_id`, `recorded_at` | Free note; the V2 row it replaced, if any; insertion time |

| Table | `rule_key` | Payload |
| --- | --- | --- |
| `master_category` | category code (`^[A-Z]{2,10}$`) | `name` |
| `master_standard` | `category:purpose` | `category_code`, `purpose`, `standard_code`, `title`, `edition` |
| `master_lab_accreditation` | `laboratory:category` | `laboratory_code` (references `organisation.code`), `category_code`, `accreditation_body`, `certificate_ref`, `accreditation_status` (`active`, `suspended`, `withdrawn`) |
| `master_fee_rule` | `category:application_type` | `category_code`, `application_type`, `amount_inr numeric(12,2)` |
| `master_rating_formula` | `category:star_rating` | `category_code`, `formula_label`, `inputs` (JSON array), `definition` (JSON), `computation_allowed` (may be true only when `verified`) |

Database guards apply to every master table:

- **No overlap.** A `BEFORE INSERT` trigger takes a transaction advisory lock on the table and rule key. It then refuses a new version whose `[from, to)` range overlaps any other version of the same key, with SQLSTATE `23P01`. Periods that only touch are allowed. An open-ended version blocks any later start. A trigger is used rather than an exclusion constraint so that no `btree_gist` extension is needed.
- **Immutable history.** `UPDATE`, `DELETE` and `TRUNCATE` are refused with `55000`: "versions are immutable … add a new version for a later period". A change is a new version for a later, non-overlapping period. Closing an open-ended version is therefore not possible yet (decision M6).
- **Upgrade path.** V4 copies the V2 `fee_rule` and `rating_formula` rows into the new tables as version 1, keeping their ids in `legacy_id`. It then drops the two V2 tables. Nothing in the existing data is lost.

## 2. Date boundary convention

A version applies on date `d` when `effective_from <= d` and either `effective_to` is null or `d < effective_to`. This is a half-open range `[from, to)`: the start date is included and the end date is excluded. When one version ends on 2026-10-01 and the next starts on 2026-10-01, the old version applies through 30 September and the new one from 1 October. Dates are calendar dates in India Standard Time. The caller converts any instant to an IST date before asking. WP05.1 and WP05.2 must still decide which business date they supply, for example the submission date or the fee-confirmation date (decision M7).

If no version covers a date, the lookup returns **no rule**. This happens before the first version and in a gap between versions. The service never falls back to the nearest version. If two versions ever matched one date, the repository would throw instead of choosing one; the overlap trigger prevents that state.

## 3. Spring API (internal)

The code is in package `gov.bee.api.masters`. It has no controller and is not referenced by any route or permission.

- `MasterDataRepository` provides `category`, `standard(category, purpose, at)`, `labAccreditation(lab, category, at)`, `feeRule(category, type, at)`, `ratingFormula(category, at)` and `history(table, ruleKey)`, using JdbcTemplate. It has read methods only and no writes.
- `MasterDataService` provides:
  - `categoryApplies`;
  - `applicableStandard`, `feeRule` and `ratingFormula`, which return empty unless the category itself applies on that date;
  - `accreditation`, which returns `ACCREDITED`, `SUSPENDED`, `WITHDRAWN` or `NO_RECORD`. A suspended or withdrawn record that is in force is **not** an accreditation.
- Each record has `beeVerified()`. `RatingFormula` deliberately has no compute method.

## 5. The ₹1,000 / ₹24,000 fee discrepancy

The two sources disagreed:

- FIRST_SLICE.md provisional decision **D6** says "one seeded rule: ₹24,000 for room air conditioners", citing DDD §5.3 (gap G08).
- The V2 local seed (`fee_rule` RAC-DEMO) held **₹1,000.00**. It has no source, and was a local placeholder.

Neither value was silently chosen, and neither is BEE-approved. Both are kept as separate, labelled versions of `RAC:new_model`:

| Version | Amount | Period | Status | Why |
| --- | --- | --- | --- | --- |
| v1 | ₹1,000.00 | `[2026-01-01, 2026-10-01)` | `synthetic`, `legacy_id = RAC-DEMO` | The existing V2 row, preserved unchanged by the V4 migration; source recorded as "local placeholder; no source" |
| v2 | ₹24,000.00 | from 2026-10-01, open-ended | `provisional` | The D6 figure; source "FIRST_SLICE.md provisional decision D6, citing DDD §5.3 (gap G08); not confirmed by BEE" |

So a lookup for 30 September 2026 returns ₹1,000 and a lookup for 1 October 2026 returns ₹24,000, each with its provenance. The split date is synthetic. It does not mean BEE changed the fee on that date. The tests assert the amounts, statuses, sources and boundary. `local:check` (`db.provisional-rules`) asserts the same state in the running database. BEE must still decide the real amount, the application types, tax treatment and effective date (M4). The real rule will be a new `verified` version; neither row will be edited.

## 6. Rating formula

The formula master holds metadata only. The seeded `0-unverified` version has an empty definition and `computation_allowed = false`. A database `CHECK` refuses `computation_allowed = true` unless the row is `verified`, and the Spring model exposes no way to compute a rating. The prototype's `computeStars` thresholds are not copied into the master. Any rating shown by the prototype still carries `0-unverified` and is not an official star rating (FIRST_SLICE.md D3). WP05.2 owns computation once BEE supplies a verified formula (M5).

The focused tests in `MastersDatabaseTest` cover:

- **Upgrade.** V2 RAC-DEMO ₹1,000 becomes fee v1 and RAC-STAR-DEMO becomes formula v1. The V2 tables are gone.
- **Version selection and exact boundaries.** For the fee: 2025-12-31 gives none, 2026-01-01 gives v1, 2026-09-30 gives v1, 2026-10-01 gives v2, and a far-future date gives v2. The standard changes from v1 to v2 exactly on 2026-07-01.
- **Gaps.** A probe key with a gap returns no rule inside the gap. The seeded accreditation gap returns `NO_RECORD` on 2026-07-01 and 2026-07-31, and `ACCREDITED` again on 2026-08-01.
- **Inactive accreditation.** `SUSPENDED` in June; `WITHDRAWN` for a probe record. A laboratory with no record gives `NO_RECORD`. An unknown laboratory code is refused by the foreign key.
- **Overlap rejection.** The test tries five overlapping shapes: inside, straddling the start, straddling the end, covering, and an identical period. All are refused with `23P01`. Touching periods are accepted. An open-ended version blocks later starts, including a v3 after the seeded fee v2. A duplicate version number is refused with `23505`.
- **Immutability.** UPDATE, DELETE and TRUNCATE on history are refused with `55000`.
- **Formula.** Marking the unverified formula computable is refused with `23514`.
- **Repeat seeding.** Applying `seed.sql` twice leaves the master rows unchanged. A fixture with ₹25,000 for v2 is refused, and the transaction rolls back.
- **Reset.** Two fresh migrate-and-seed rebuilds produce exactly the same masters as the upgraded schema.

## 8. Limits

- There are no administration writes. Rows enter only through migration and seed SQL, and tests insert probe rows directly.
- Corrections and closing an open-ended version are not supported (M6).
- Accreditation is keyed to the seeded `LAB` organisation. WP04.2 owns organisation workflows.
- Standards are keyed by category and purpose only, without model sub-types or star bands.
- `RT1` (`rt1-proof.sh`) has been updated to count the new tables but was not run, because it is destructive.
- There is no audit event for master changes; WP04.3 owns master-data audit tests.
