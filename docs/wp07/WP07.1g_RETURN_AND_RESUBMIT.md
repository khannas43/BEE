# WP07.1g — Return to the applicant, edit and resubmit (Wave 1)

**Status:** Implemented locally on branch `wp07.1g-return-reject`; local checks pass (see Evidence). **Not independently reviewed or accepted.** WP05.2 and the first slice remain open; the work-package count stays 1/11.

**Provisional local rules, not BEE rules.** The questions BEE must answer are in [../BEE_DECISIONS.md](../BEE_DECISIONS.md) (B7, A2). This work package builds the recommended default for B7 ("allowed while the application is in the returned state, never after resubmission"). **Rejection is not in this package**; it is the next one (BL-117).

## What it does

Every stage that can say no now has a way back, as [FIRST_SLICE.md](../wp01/FIRST_SLICE.md) section 4 specifies.

**Return** — `POST /api/model-applications/{id}/return` (browser route `/api/runtime/model-applications/{id}/return`), with a version and a reason.

| Rule | Behaviour |
| --- | --- |
| Who | The owner of the stage the application is in, by the same checks as a forward step: the assigned IAME officer (`iame_scrutiny`), the assigned Reviewer (`bee_scrutiny`), the Director (`director_review`), the Secretary (`secretary_approval`). Finance and Programme do not return (Programme will reject instead). Anyone else, including the applicant, gets 403 `role_not_permitted`. |
| Separation | The applicant's own organisation, or anyone who acted at a different stage, gets 403 `segregation_refused`. An officer who is not assigned gets the same 404 as an unknown application. |
| Reason | 1 to 500 characters, no control characters. The applicant sees it. |
| Atomic write | One transaction: the state becomes `returned`, an append-only transition event, and an append-only return record that keeps the stage it came from, the reason, and a **fingerprint of the rating inputs** at that moment (declared efficiency, laboratory, test date, number of test-report versions). The officer's assignment is left open. |

**Edit while returned** — the existing draft edit and document upload now also accept a `returned` application (decision B7). The applicant may correct the evidence and add reports, but **not** the brand, category or model number it was filed under (422 `validation_failed`). After resubmission it is not editable again (403 `not_editable`).

**Resubmit** — `POST /api/model-applications/{id}/resubmit`, with a version and an optional note.

| Rule | Behaviour |
| --- | --- |
| Who | The filing applicant only (403 `no_write_scope` for anyone else). Only a returned application (403 `not_returned`, a new code). |
| Checks | The brand must still be the filer's, and the same six evidence gates as the first submit run again on the edited application (test report, declared efficiency, test date, accredited laboratory, standard in force, no duplicate model). The fee is not charged again. |
| Where it goes | Back to the stage that returned it. **If it was returned from the Director or the Secretary and a rating input changed since the return, it goes to `rating` instead**: the earlier rating is superseded (it stays as version 1; Programme computes version 2) and an approver never decides on a rating that no longer matches the evidence. A change before the rating existed supersedes nothing. |
| Atomic write | One transaction: the state, an append-only transition event (`resubmit`), and an append-only resubmission record, exactly one per return. |

**The same officer may act again.** Previously, anyone with an earlier event on an application was refused at every later step. That wrongly blocked an officer who returned a case from acting on it again, and Programme from rating a second time. The rule is now what the spec says: refused if the person acted at **another** stage; an earlier action at the **same** stage never counts. A Director who returned a case at the Director stage still cannot approve it as the Secretary.

**What the applicant sees.** The application detail now carries the open return (`returnNote`: the stage and the reason) while it is returned, on the detail read only. The dashboard shows the reason and an "Edit and resubmit" link; the form shows a banner with the reason, locks the brand and model number, and offers "Resubmit" in place of "Submit" (an unsaved change blocks it). The four officer screens (IAME, Reviewer, and the shared Director and Secretary screen) each gained a "Return to the applicant" panel.

## What changed

- **Flyway V31:** `model_application_return` and `model_application_resubmission` (both append-only; the resubmission points at exactly one return; a check ties "rating superseded" to "resumed at rating") and the disposable-cleanup function extended.
- **Spring:** `gov.bee.api.rework` (return and resubmit: controller, service, repository), `StageReturn` (the four return rules, separate from the seven-step `SliceAction`, whose test asserts it stays seven), and the changed "acted at another stage" query in every step's repository.
- **Contract 0.14.0:** both operations on both layers, their requests and receipts, `ApplicationReturn` on the detail read, and one new error code, `not_returned`.
- **Screens:** `ReturnToApplicant` (shared), the resubmit panel on the draft form, the dashboard's reason and edit link.

## Evidence (4 October 2026, local single-Mac runtime)

- `npm run api:test`: 101 pass. The real-database suites: 110 pass, including 13 new tests in `ReworkDatabaseTest`: each stage owner returns from its own stage with event, record and fingerprint and the assignment kept; a stale version or wrong state writes nothing; resubmitting goes back to the stage that returned it from all four stages; a changed rating input after the rating sends it back through rating and keeps both ratings; a change before the rating existed supersedes nothing; a report added while returned counts as a changed input; editing is possible while returned and never after; one resubmission per return; the records are append-only and refuse bad values; two simultaneous returns have one winner; the same-stage rule; and the cleanup.
- `SpringContractTest` exercises every documented status and code of both operations, including all four return roles and all six evidence gates on resubmit. `SlicePolicyTest` (33) covers the four return rules.
- `npm run web:test`: 149 pass; `npm run web:test:ui`: 25 pass.
- `npm run local:return-resubmit`: **105/105** (two runs, real Keycloak sign-in with TOTP for seven people). Scenario A: the IAME officer returns through the real screen, the applicant sees the reason on the dashboard, edits through the real form (brand and model locked, an unsaved change blocks Resubmit), resubmits, the same officer sees it again and recommends. Scenario B: the Reviewer returns through its screen and forwards after resubmission. Scenario C: the Director returns through its screen, the applicant corrects the declared figure, the application goes back through rating (rating version 2, version 1 kept) and the same Director recommends. Scenario D: the Secretary returns through the shared screen and, after an unchanged resubmission, approves; the history reads `confirm_fee, iame_recommend, reviewer_forward, compute_rating, director_recommend, return, resubmit, secretary_approve`. Scenario E: replay and key conflict for both commands.
- `npm run local:check`: **915 passed, 0 failed**; contract coverage 248/248 internal pairs and 340/340 browser pairs; 1327/1327 live observations conform; `wiring.routes` 195/195 across 36 routes; `matrix` and `audit:access` pass.
- Lint: no new findings (3 existing warnings in `StageScreen.tsx` and `WorkflowScreens.tsx`); `tsc` is clean.

## Found and fixed on the way

- The live check caught what the database tests could not: Programme was refused when the rating had to be redone, because its own earlier rating counted as "another stage". Fixed as described above, with a test.
- Two checks used `/rating` and `/return` as stand-ins for routes that did not exist yet; they now use `/rating/override` and `/return/override`, which must stay denied.

## Limits

Tracked as BL-114 to BL-119 in [../BACKLOG.md](../BACKLOG.md): there is no rejection yet, no limit or deadline on how long an application can stay returned or how many times it can be returned, no notification to the applicant, the set of "rating inputs" is a provisional choice, and the approval is not stored against a specific rating version.
