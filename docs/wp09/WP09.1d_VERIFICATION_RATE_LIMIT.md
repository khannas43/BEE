# WP09.1d — A limit on the public verification route (BL-143)

**Status:** Implemented locally on branch `wp09-verification-rate-limit`; the full local gate result is in Evidence. **Not independently reviewed or accepted.**

**Provisional local rules, not BEE rules.** The public verification route ([WP09.1c](WP09.1c_PUBLIC_VERIFICATION.md)) is the one unauthenticated endpoint, so nothing slowed a script that tried many registration IDs. The numbers below are the owner's defaults, not BEE decisions.

## What it does

- **The portal limits first** (`app/api/runtime/verification`): a fixed one-minute window, counted before anything else so a flood costs one counter. Every request counts, valid or not.
  - **No trusted proxy (the local setup):** all visitors share one window of **300 a minute**. Next.js route handlers cannot see the connection's address, and the forwarded-address header can be invented by a caller, so a per-visitor key would be dodged by changing the header. One shared window cannot be dodged.
  - **Behind a proxy that overwrites the header (`BEE_TRUST_PROXY=1`):** each forwarded address has its own window of **60 a minute**; a missing or malformed address falls back to the shared window.
  - Limits can be changed with `BEE_VERIFY_LIMIT_PER_ADDRESS` and `BEE_VERIFY_LIMIT_SHARED`. The table of windows is bounded (10,000 keys), so a flood of invented addresses cannot grow memory.
- **Spring keeps a backstop** (`PublicRateLimiter`): at most **600 a minute** for the whole service, in case something calls Spring directly (property `bee.public-verification.limit-per-minute`).
- **The answer:** `429` with `{ "error": "rate_limited", "message": "Too many requests. Wait a moment and try again." }` and a whole-second `Retry-After` (at least 1, at most 60). The portal passes Spring's wait on, or says 60 if Spring sent none.
- **The page** says "Too many checks just now. Please wait a moment and try again (about N seconds)." (the wait is shown only when the server gave a sane one).
- Contract 0.25.0: a `429` with a required `Retry-After` on both layers, the new code in the error catalogue and in the `Error` schema.

## Limits, recorded

- **In memory and per instance.** Several instances would each allow the limit; a shared store and edge limits belong to the production hardening (BL-130). When a proxy is added, `BEE_TRUST_PROXY=1` must only be set if the proxy overwrites `X-Forwarded-For`.
- The shared window means one noisy visitor can use up the minute for everyone, locally. That is the price of not trusting a header we cannot verify; per-visitor windows apply once a trusted proxy is in front.

## Tests and evidence

- Node: `rate-limit.test.mjs` (window, refusal with the seconds left, reopening, separate keys, the memory bound, never below 1 second; without a proxy an invented address buys no fresh window) and `rate-limit-proxy.test.mjs` (the first forwarded address is the visitor; malformed or missing falls back to shared).
- Java: `PublicRateLimiterTest`; `SpringContractTest.publicVerificationRateLimitDocumentedPairs` (404, 404, then 429 with `Retry-After` 60, the wait shrinking on a fake clock, a blank request counting too, reopening).
- Vitest: the page shows the wait when the server gave one and omits it when it sent junk.
- Stand-in: the portal passes an upstream `429` through with a `Retry-After`.
- Live (Secretary check, now 131 checks): a burst of unknown IDs through the portal gets a `429` after 286 requests (14 earlier in the run had already been counted) that conforms to the contract, `Retry-After` is a whole number of seconds from 1 to 60, the route keeps refusing while the window is full, and answers normally once the wait has passed. The proof runs last and waits the window out.
