# WP02.4 — Brute-force detection and complete denial evidence (14 October 2026)

**Provisional local rules, not BEE rules.** This note closes two of the gaps listed in [WP02.3_MFA.md](WP02.3_MFA.md) §10: Keycloak brute-force detection was off, and the denial cases N1 to N10 and A7 were proved only in part (several by unit tests or by the policy's own wording, "endpoint stays denied"). Delegation and escalation are separate (below).

## 1. Brute-force detection (Keycloak)

| Setting (local/generate-fixtures.cjs `BRUTE_FORCE`) | Value |
| --- | --- |
| Temporary lockout, never permanent | on |
| Failures that lock the account | 10 within 15 minutes |
| First wait, then it grows by the same step | 60 seconds, up to 15 minutes |
| Quick-login lock | effectively off (1 ms / 1 s), so fast scripted failures in local checks do not lock a user by timing alone |

The realm import file carries the values; `npm run local:up` also applies them to an existing realm (`scripts/local/ensure-realm-policy.cjs`), because the import runs only for a realm that does not exist yet. `scripts/local/bruteforce-check.cjs` (`npm run local:bruteforce`, part of `local:check`) proves it on a disposable twin: ten wrong passwords lock the account; the correct password with a valid one-time code is then refused; another account is unaffected; an administrator clears the lock; sign-in works again. The values are the owner's local assumption, not a BEE rule.

## 2. The denial suite (N1 to N10, A7)

`scripts/local/denial-suite-check.cjs` (`npm run local:denial`, part of `local:check`) calls Spring directly with disposable twins' tokens. The matrix is every persona (13) by every command route (submit, edit, fee confirmation, IAME, Reviewer, rating, Director, Secretary, return, reject, resubmit) by every seeded application (4), minus the few combinations where the persona is the entitled actor at that stage. Every one of those 566 calls must answer 401, 403 or 404. Afterwards the applications, submission events, transition events and fee snapshots are identical, and the history of each application is byte-identical (A7).

| Case | Proved by |
| --- | --- |
| N1 cross-organisation list, read, edit | `access-check` (list, read); `denial.N1-cross-organisation-edit` and the edit row of the matrix |
| N2 agency without authorisation | `model-drafts-browser-check` (create and submit), `registration-review-browser-check` section 4 (absent, not-yet-started, revoked) |
| N3 only Finance confirms the fee | `denial.fee-confirmation`, `denial.N3-fee-confirmation-only-finance` |
| N4 Finance has no technical action | `denial.N4-finance-has-no-technical-action` and the matrix |
| N5 IAME approving or on an unassigned application | `denial.N5-iame-no-approval-and-only-assigned` and the matrix |
| N6 deciding before a rating, or on a superseded rating | `denial.N6-N7-N9-deciding-out-of-order`; `return-resubmit-browser-check` (`goes-back-through-rating`: a superseded rating sends the application back through rating) |
| N7 order of Director and Secretary | `denial.N6-N7-N9-deciding-out-of-order`, `denial.director-recommendation`, `denial.secretary-approval` |
| N8 the same person at two stages | `denial.N8-same-person-two-stages-secretary` and `-director`: a seeded application is moved to the stage and an earlier step by the same twin is written; the answer is 403 `segregation_refused`; `denial.N8-restored` proves everything was put back |
| N9 outside the role's current stage | the whole matrix (575 calls) |
| N10 Helpdesk, Admin, Auditor | `denial.N10-helpdesk-has-no-transition`, `-admin-`, `-auditor-` and the matrix |
| A7 every denial leaves history unchanged | `denial.A7-nothing-changed`, `denial.A7-history-unchanged` |
